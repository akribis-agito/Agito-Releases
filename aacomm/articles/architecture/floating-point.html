AAComm Floating-Point Resolution

Principle

Data that leaves AAComm via the Extension classes (e.g., RecordingDataContainer, LoggerDataContainer, ScopeDataContainer, AllStatInterpreter) is properly resolved and ready to use. Raw IEEE 754 bit-pattern resolution is handled transparently by these classes.

Limitation: Resolution only applies when data is obtained through the Extension mechanism, or for protocols that have Rx-path resolution (see below). If an unsupported upload command is issued directly via CommAPI.Send() — such as from PCSuite Terminal — the raw response is not resolved. The consumer receives unprocessed bit-masked values.

The SDK exposes ConFltSnapVal and ProgSnapVal as raw values only and does not resolve them: their source parameters (ConFltSnapSrc / ProgSnapSrc) are user-configurable, so the slot types are known only after the CCC sources are read, and that read-and-resolve step belongs to the caller (PCSuite's FaultDataView and UpSnapshotDecode do it).

Number text

Every value crosses the AAComm boundary as text — AACommEventArgs carries a reply only as MsgReceived — so each read is a format-then-reparse round trip. Both halves are pinned to CultureInfo.InvariantCulture: '.' as the decimal separator, never a group separator, matching the controller's own ASCII protocol.

Formatting. Every floating-point value AAComm emits as text goes through WireNumber.ToWire (AAComm.Internal.Wire): scaled replies and ParamAbout bounds from FloatHelper, the resolved AllStat values in AllStatInterpreter, the User Units factor written by TrySetUnitsSync, the recording-trigger download commands in TriggerContainer. It picks the shortest fixed-precision invariant form that parses back to the same value — G15 else G17 for double, G7 else G9 for float — so two guarantees hold by construction: the text round-trips to the identical value (checked per value, not assumed), and it is byte-identical on every target framework, because every target runs that same selection over specifiers that are themselves target-stable. Neither holds for "R", which is shortest-round-trippable on .NET 8/10, a documented round-trip hazard on 64-bit .NET Framework, and disagrees between the two for 16-significant-digit values; a bare ToString() is worse still — 15-digit lossy on .NET Framework 4.8. Integral wire tokens and the legacy FirmwareVersionStr/FPGAVersionStr are likewise rendered with CultureInfo.InvariantCulture, so a negative value never carries the U+2212 minus sign that ICU uses for sv-SE, fi-FI, nb-NO, et-EE and lt-LT — the reply text is truncated to bytes one char at a time, which would turn -12345 into \x1212345.

Parsing. Where AAComm parses a controller-supplied decimal number it uses an explicit NumberStyles.Float | NumberStyles.AllowThousands and the invariant culture: the assignment value in CanMessageParser, the factor read back in UserUnitGroup, the About-data bounds in MessageData, and the values AllStatInterpreter decodes. The transmit seam in PayloadBuilder is the one deliberate exception: it reads the outgoing assignment with plain NumberStyles.Float, no AllowThousands, because a , is an assignment separator in the controller's own grammar — reading 1,5 as one thousand five hundred there would rewrite a command the parser rejects into one it accepts.

Consumers must do the same. A reply reaches the caller as text; parsing it in the current culture reads an invariant 0.01 as 1 on a comma-decimal locale, or throws.

Resolution

Core logic lives in FloatHelper (AAComm.Services) — public static class, callable directly by all consumers.

FloatHelper.ResolveFloatingPoint(MessageData md, long val, bool doubleSupported, bool floatSupport) determines the correct conversion based on the parameter's MessageData type:

  • float/double with doubleSupported — LongToDouble() (64-bit IEEE 754)
  • float with !doubleSupported and floatSupport — IntToFloat() (32-bit IEEE 754)
  • float with !doubleSupported and !floatSupport — returned as-is (float hole protection)
  • int / long — returned as-is
  • null metadata (unknown parameter) — returned as-is (safe fallback)

FloatHelper.ResolveFromCCC(int ccc, long rawVal, IMessagesContainer dataContainer, bool doubleSupported, bool floatSupport) resolves via Complex CAN Code: parses CCC -> looks up MessageData -> delegates to ResolveFloatingPoint.

Throws FormatException on NaN or Infinity.

Float Hole Protection

AllStat_64bit protocols (AllStat, Logger, Scope, ConFltSnap, ProgSnap) never transmit 32-bit float bit patterns. They either send raw integers or 64-bit doubles. These protocols pass floatSupport: false, which blocks the IntToFloat path and prevents garbage values when doubleSupported=false and a parameter has float metadata. RecUpload and ParamAbout pass floatSupport: true.

Firmware-Side UserUnits (Recording Header)

The per-vector UserUnits integer stored in the recording header (VectorDataContainer.UserUnits, read from GetUserUnitsIndex(i)) is part of a parallel firmware-level scaling system. It is mutually exclusive with the PCSuite UU feature at the firmware level. This value is preserved as metadata in RecParamHeader and AGF files but is NOT used for PCSuite UU scaling. PCSuite UU factors are looked up dynamically through the centralized FloatHelper.ResolveUserUnitsFactor() — CommAPI.GetUserUnitsEnabled() + ControllerMessagesContainer.TryGetUserUnitAxis(), plus the per-message AACommMessage.SkipUserUnits opt-out — which FloatHelper.ApplyUserUnits() wraps for the callers that only need to multiply.

User Units: Embedded vs Global

Firmware declares two independent user-units systems. They are one declaration each of two different things, not two declarations of one — different membership between them is by design.

System Declared by Who converts
Embedded the bInUserUnits field of each keyword's KW_ROW attribute row — USER_UNITS / AUX_USER_UNITS / PD_USER_UNITS / SCALING / NO_USER_UNITS / FUNC_UNITS (Firmware-Main:CommonC/AG300_CTL01Params.c) the controller, on the comm path, by the per-axis UsrUnits / AuxUsrUnits / PDUsrUnits ratio — live values reach AAComm already converted; the About table and ParamAbout report a SCALING parameter's bounds raw, in the controller's internal unit, and MessageData / FloatHelper.ResolveParamAbout divide them by ScalingFact once
Global the gl*UnitGroup[] CAN-code arrays (Firmware-Main:CommonC/AG300_CTL01UtilityFuncs.c) AAComm, on the Tx and Rx paths, from the group membership and per-axis factor it reads at connect

For the SDK the group arrays are authoritative. UserUnitsAdapter.RefreshSync reads the UnitGrp[] membership arrays, the UnitFct factor and the UnitUnt[] unit names, and nothing else. The keyword flag describes controller behaviour and is not an AAComm input — deriving a parameter's AAComm units contract from it gives the wrong answer. The two sets differ (one firmware revision flags 92 KW_ROW rows for the embedded system while the eight group arrays hold 80 CAN codes between them) and they move independently, so treat the counts as an illustration, never as a number to rely on.

The systems are mutually exclusive per parameter and firmware enforces it: CheckGlobalUserUnitsConflict (Firmware-Main:CommonC/AG300_CTL01Interpreter.c) rejects an assign or a read with error 338, GLOBAL_VS_EMBEDDED_USERUNITS_CONFLICT, when the keyword is flagged for the embedded system, its embedded ratio is non-default, its CAN code is in the Global group array matching that flag, and UserUnitsEn is set for that axis.

EtherCAT controllers implement the embedded system only: Firmware-Ethercat:Source/Params.c declares the embedded flags and the UsrUnits / AuxUsrUnits / PDUsrUnits parameters, but no UserUnitsEn, no group arrays and no factor parameters. RefreshSync bails with UUErrors.NoUserUnits and the Global layer never engages.

PCSuite's view of the Global system, group by group: PCSuite/Core/Configuration/UserUnits/user-units.md.

User Units Transmit Seam

PayloadBuilder applies the Global system on the way out, above the transport branch — the same step in BuildPayload (string IPC) and BuildTypedPayload (binary IPC), run before either asks which channel it is on. An assignment is divided by the factor of its own parameter (FloatHelper.ResolveUserUnitsFactor, the lookup the receive path uses) and re-rendered with WireNumber.ToWire; the API-only config gate (*UnitFct / *UnitUnt[], error 4023, bypassed per message by AACommMessage.AllowUserUnitsConfig) rejects there too. CanMessageParser reads the assignment as-is — the text reaching it is already in controller units.

The seam resolves the command from a copy with every space removed — the tokenisation CanMessageParser itself uses, so APos =1.5 is the same write as APos=1.5 and meets the same gate and the same factor. A command it rewrites crosses in that normalised form; one it does not rewrite crosses byte-for-byte as the caller wrote it.

A command the seam cannot resolve — a query, an unknown mnemonic — crosses untouched: the CCC builder owns its error (MnemonicNotFound for an unknown one), and on the bare-ASCII transports there is no error to raise. Two rules follow from where the gate sits:

  • An assignment to a User Units config parameter is rejected 4023 before the value is validated. A malformed, out-of-range or wrong-form value on a real *UnitFct / *UnitUnt[] reports 4023 rather than the parser's 8/9/14/25 — the gate must not depend on a validation the bare-ASCII transports never run.
  • A value the seam cannot read as a finite number (1e400, Infinity, NaN, 1,5) is left exactly as written for the CCC builder to judge, never rendered onto the wire in a rewritten form.
  • An assignment to a firmware-integral parameter (ParamType 0 or 3 — MessageData.IsInt / IsLong) crosses as an integer, rounded to-even in controller counts, on every transport. The rounding belongs here, below the division: rounding a display value above the seam rounds in the wrong space (at a 0.01 mm/count factor it quantises to 100 counts, not 1). CanMessageParser already rounds that way when it packs a CCC frame, so the seam only closes the gap the string transports leave — 244.39 / 0.01 is 24438.999999999996, which used to reach an RS-232 controller as that text while the same command inside a CCC frame carried 24439. The rule applies at factor 1 too, because the caller's value is a display value and may carry a fraction the firmware cannot hold. Float and double parameters keep their fraction, and a value that is already integral is not a rewrite — the command crosses with its original bytes.

What a message type does is an explicit table, not a consequence of which branch reaches the CCC builder:

Message type Transmit User Units
Regular, ResetRequest, EraseUserProg, Continuous scaled once, above the transport branch
EthernetASCII scaled once for the single-command key (A), after the key char is set aside; the ASCII-bulk keys (L, I) carry a ;-joined list this seam does not parse and cross raw
BulkMessage, BulkMessageIgnore scaled per sub-message inside the bulk segment loop, so a rejected segment keeps the halt-on-error / ADoNothing semantics
Firmware, UserProgram, UserProgramBin, SpecialBulk, SpecialBulkB, BulkMessageCNC, BulkMessageCNCB, InternalAACS raw in both directions — scaling a download payload corrupts it

The recording download opts out per message: AACommDataRecManager sends its parameter batch with skipUserUnits: true, because TriggerContainer's Tx constructor has already de-scaled RecTrigVal / RecTrigValMax and a second pass would square the factor.

User Units Cache Lifetime

The Global User-Units factors are read from the controller and cached in ControllerMessagesContainer.UserUnits. The cache is populated by CommAPI.Connect, cleared by Disconnect, and re-read after a controller reboot the session survives — a completed MessageType.ResetRequest, sync or async (Session.SendReceive / Session.RunUserCallback). A reset that came back an error leaves the cached values in place; a re-read that cannot reach the controller clears them rather than leaving the pre-reset factors behind. The firmware / FPGA download EOF steps also reboot the controller, but those flows end in CommAPI.Disconnect, which clears the cache on the way out. A refresh rebuilds the configuration off to the side and publishes it in one swap, so a reply being scaled on the receiver thread meanwhile resolves against the complete old configuration or the complete new one — never a half-filled cache.

A raw write to *UnitFct / *UnitUnt that bypasses the config gate (AACommMessage.AllowUserUnitsConfig) does not update the cache — provisioning tools resync it with CommAPI.RefreshUserUnits().

LoggerUpload / ScopeUpload

Both use PacketDataParser for the common wire format: nPackets, [header, val1, val2, ...], ..., 0. Header is packet ID (Logger) or Time (Scope). Resolution is applied per value using the caller-provided MessageData list.

PCSuite adapts these containers into its UI models. The CSV import path in LoggerData bypasses AAComm resolution (values are already resolved in the file).

AllStat

AllStatInterpreter requires a connected CommAPI (constructor delegates validation to RecParamsResolver.ValidateAPI). Every field in AllStatAxisData is resolved via mnemonic lookup against the controller's MessagesContainer — float/double fields get bit-pattern conversion, integer fields pass through as double.

Rx-Path Resolution (ConvertReplyToFloatIfNeed)

FloatHelper.ConvertReplyToFloatIfNeed is the inline Rx-path resolver for all message replies. It intercepts raw controller replies before delivery to the caller and converts IEEE 754 bit patterns to floating-point values. This ensures that even low-level SendReceive() consumers (e.g., PCSuite Terminal) receive properly resolved data.

Resolved in the Rx path:

  • Single-value parameters: float (IntToFloat) and double (LongToDouble) based on MessageData type. Note: the single-value path dispatches purely on MessageData.IsFloat/IsDouble — it does NOT check the doubleSupported/floatSupport flags. An unscaled float parameter is rendered by WireNumber.ToWire(float), in its own width: the reply carries at most 9 significant digits and re-parses to the bit pattern the controller holds, where the widened double form of 1e-9f is 9.9999997171806854E-10 — below that parameter's own declared minimum, and rejected on the way back down. A scaled float value (User Units factor other than 1) is a genuine double and is rendered as one: narrowing the product would cost the ulp that carries the transmit-side division back to the stored float32.
  • ParamAbout: multi-value State,MIN,MAX,DEFAULT — delegated to FloatHelper.ResolveParamAbout
  • AllStat: multi-value comma-separated longs per axis/group — delegated to AllStatInterpreter.ResolveRawReply. Uses the static mnemonic arrays and the private Resolve() instance method to convert each value in group order. Bit-pattern conversion runs only when AllStat_64bit_Supported; User Units scaling is applied either way, matching the structured ParseAllStatData path.

NOT resolved in the Rx path (CAN code unknown at Rx flow time):

  • RecUpload: not resolved here — RecordingDataContainer parses raw longs and resolves per-vector with the correct feature flags. Rx-path resolution would double-convert (long→string→long parse failure)
  • RecUploadNext: sequential packet protocol — the CAN codes are not embedded in the N2 data packets
  • ScopeUpload / LoggerUpload: the CAN codes are supplied by the caller, not present in the reply
  • ConFltSnapVal / ProgSnapVal: raw values only; the source CCCs are user-configurable, and resolving against them is the caller's work

Error Handling

AAComm throws generic FormatException on invalid floating-point values (NaN, Infinity). Consumer applications (e.g., PCSuite) catch and localize these messages.

Recording Data Header Versions

Last validated: 2026-03-14

Overview

The HeaderV1/V2/V3 classes define array index mappings for parsing recording data uploaded from the firmware. The firmware populates gllRecData[] using 1-based indexing (index 0 is unused and never transmitted). The C# side receives the data as a 0-based List<long>, so: C# index = FW index - 1.

Header version is selected at runtime by RecParamsResolver based on controller identity:

  1. HeaderV1 if MaxNumOfRecVectors <= 8
  2. HeaderV3 if MessagesContainer contains both RecDataB and RecTrigsLogicS
  3. HeaderV2 as fallback

RecParamsResolver.HeaderV3(ControllerMessagesContainer) is a public static helper that mirrors the V3 detection logic for external callers.

Firmware repo: C:\DEV\Firmware\Firmware-Main Firmware sources: CommonIncludes/AG300_CTL01ParamsCommon.h (defines), CommonC/AG300_CTL01Funcs.c (RecStart, RecUpload).

RecDataNumOfRequestedPointsIdx is a virtual property on HeaderBase (default = 1, not overridden by any version). RecDataNumOfRecordedPointsIdx is abstract — the progress-query index used by RecParamsResolver.RecDataNumOfRecordedPoints to read how many points have been recorded so far. In V2/V3 it coincides with RecTrigPosIdx; in V1 it coincides with RecTrigPosIdx at C# index 25 (FW[26]).

Note 2 — RecDataNumOfRecordedPointsIdx: In V2 and V3, the progress-counter index (C# 3 = FW[4]) coincides with RecTrigPosIdx. In V1 it is C# 25 = FW[26], which also coincides with RecTrigPosIdx. The slot is read for different purposes at different times: trigger position during header parsing, recorded-point count during progress polling.

Note 1 — RecLengthIdx across all versions: C# RecLengthIdx reads FW REC_REQUESTED_LEN_INDEX (requested recording length), not REC_LEN_INDEX (total data length = numVectors * recLength). This works because at upload time the recording is always complete, so requested length = actual length. Not worth fixing.

V2 Mapping

Validated against: commit 428f39b4f ("From here starting to work on advanced data recording triggers - new keywords") — the last commit before the V2→V3 header restructure (fbc553c33). Defines in AG300_CTL01ParamsCommon.h lines 2227-2241, header assignments in RecStart() at AG300_CTL01Funcs.c lines 6470-6497.

V2 is an intermediate development step between V1 and V3. It introduced REC_HDR_SIZE = 80 and REC_PARAM_SIZE = 21 (20 vectors), but predates multi-trigger and multi-RecSystem support (only one recording system existed; RecSysID did not exist). No multi-trigger: RecTrigsModeIdx = -1, RecTrigsLogicRelationBeginIdx = -1.

V1 Mapping

Validated against: commit 692b6924 (2022-11-24) — the last commit before the V1→V2 header restructure (dd893e3b, 2022-11-27). No named REC_*_INDEX defines existed; all indexes were hardcoded in RecStart() at AG300_CTL01Funcs.c lines ~6482-6513. REC_HDR_SIZE = 40, REC_PARAM_SIZE = 9 (8 vectors + 1 for 1-based indexing).

FW supports 8 recording vectors in V1. User units have a split layout: vectors 1-4 at FW[20-23] (20+j), vectors 5-8 at FW[27-30] (20+j+3), with FW[24-26] occupied by other fields in between.

V1 FW Header Layout

FW[1]     gsNumOfRecParams * glRecLength    (total expected data length)
FW[2-9]   glRecParam[1..8]                  (CCCs to record, 8 slots)
FW[10]    glRecLength                       (requested recording length)
FW[11]    glRecGap
FW[12]    glRecTrigSrc
FW[13]    glRecTrigMask
FW[14]    glRecTrigTyp
FW[15]    glRecTrigVal
FW[16]    glIdentity[IDENTITY_CURR_LOOP_FREQ_INDEX]  (sample rate)
FW[17]    REC_HDR_SIZE + 1 = 41             (index of first element)
FW[18]    trigger location index
FW[19]    last recording index
FW[20-23] user units for vectors 1-4        (20+j, j=0..3)
FW[24]    ALL_USER_UNITS_SCALING
FW[25]    (unused)
FW[26]    glRecTrigPos / points recorded counter (dual-purpose — see note 2)
FW[27-30] user units for vectors 5-8        (20+j+3, j=4..7)
FW[31]    glRecTrigValMax
FW[32-40] unused
FW[41+]   recorded data

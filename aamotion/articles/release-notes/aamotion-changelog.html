[12.0.0] - 2026-10-30

⚠️ Breaking

  • The 11.0.0 → 12.0.0 upgrade page walks the whole release for a consumer — every break with the diagnostic it raises, the changes that raise none, and compiled before/after samples. It is published with the 12.0.0 release as aamotion-12-change-disclosure.html; download and open it in a browser, as GitHub serves an .html release asset as a file rather than rendering it.
  • Requires Agito.AAComm 15.x (see its changelog for the breaking communication-layer changes: the IIdentityContainer member, MessagesInBulk on a Simulation channel, the AllStatInterpreter input contract).
  • The AssemblyVersion is pinned to 12.0.0.0 for the whole 12.x line (package and file version keep the full number). .NET Framework consumers must recompile against 12.0.0 — a binary built against 11.0.0.0 does not bind, and no binding redirect bridges the identity change. .NET 8/10 consumers see no difference.
  • A type of yours that implements one of the seven retyped interfaces — ISingleAxis, IVector, IIOModule, IECAM, IGroupAxis, ICiGroupAxis or ICiSlave; a wrapper, an adapter, a test double — no longer satisfies it until every affected member carries the new type: 73 members lose dynamic, 59 properties move from int to double, 56 array members move from AAValueArray<int> to AAValueArray<double>, the four gantry gains become per-set AAValueArray<double> members and 34 methods widen their parameters — 226 members, none of them counted twice. The compiler reports each unsatisfied member at the class declaration, so this surfaces as one wall of errors on that type rather than at call sites.
  • Parameter values are now carried as double end to end. Every array property that was AAValueArray<int> — Identity, GenData, ErrLog, DInMode, HomingDef, LoggerParams, LoggerStatus, EventTable and the rest, on ISingleAxis, IIOModule, IGroupAxis, IVector, IECAM, ICiSlave, ICiGroupAxis and MotionController — is now AAValueArray<double>, and yields the parameter's exact value instead of a rounded int. Assigning an element into an int needs an explicit cast.
  • dynamic is gone from the AAMotion surface. Every dynamic member is now statically typed: the value properties (Pos, AuxPos, PosRef, Speed, Accel, Decel, MaxVel, MaxAcc, Force, MotorCurr, ContCL, Ia…Vq, the Vec* members on IVector, …) are double; the array-valued ones (ISingleAxis.Vel, ISingleAxis.AInGain, and IIOModule.AInPort / AInFilt / AInOffSet / AInDB / AInGain) are AADynamicValueArray; MotionController.GenDataD is AADoubleArray. Code that relied on late binding — calling a member the static type does not have, or letting a dynamic convert silently to int — no longer compiles, and a narrowing conversion now needs an explicit (int). In exchange the members are IntelliSense-visible and bind at compile time.
  • Quantity-carrying properties are double; modes, indices, counts, bitmasks and millisecond durations keep their integer type (int, or uint for the homing timeouts). The properties that moved from int to double are the positions and distances (MasterPos, PosErr, RelTrgt, MaxPosErr, InTargetTol, LockVal, ModRev, AuxModRev, ComtAng, EventNextPos, EventBegPos, EventEndPos, EventGap, SpeedChgPos, CurrPosTh, CurrPosErrTh, PosPosTh, ForcePosErrTh, RetractTarget, MapErrOffset, MapErrOffRamp, MapErrOnStep, CNCAPosRef, CNCAdPosRef, CNCBAbsTrgt, CNCBPosRef, CNCBdPosRef), the velocities and profile magnitudes (StuckVel, SpeedChgNew, RetractSpeed, CNCASpeed, CNCBSpeed, CNCBEndSpeed, CNCBAccel, CNCBDecel, CNCBJerk, CNCAEmrgDec, CNCBEmrgDec), the gains and force parameters (ForceGain, ForceKi, ForceKd, ForceFFW, ForceVelFFW, ForceRefFilt, MaxForceErr, MaxForceErrOL, ForceAInTh, CurrCurrTh, CurrAInTh), and the voltages and temperatures (VBus, VLogic, MinVBus, MaxVBus, MaxVBusAbs, RegenOn, RegenOff, BoardTemp, PwrTemp, MotorTemp, MaxPwrTemp). A caller that stored one in an int must widen it or add a cast; one reading a scaled User-Units axis now receives the fractional value instead of a truncated one. Status, mode and configuration properties (MotionStat, StatReg, ConFlt, LimitsStat, MotorOn, MotorType, EncType, EncRes, EncDir, UsrUnits, EmulRat, ProtectMask, InTargetTime, StuckTime, RptWait, MaxVBusTime, PeakTime, MaxPWM, and the *Flag / *Dir / *Src / *Type / *Stat / table-index members) keep int. The four gantry gains (GantryAccFFW, GantryPosGain, GantryVelGain, GantryVelKi) move from int to a per-set AAValueArray<double> instead; see the next entry.
  • ISingleAxis.GantryAccFFW, GantryPosGain, GantryVelGain and GantryVelKi are per-set AAValueArray<double> members, get-only. On firmware with gain scheduling — the AGM800 — each gain holds one value per gain-scheduling set, and the controller lists it as an array of five: read or write set n as axis.GantryPosGain[n], n from 1 to 5. There the member's .Value raises InvalidOperationException, as on every array member. On the AGD200 and AGD155-EC the gain is a scalar: read and write it through .Value. As int properties they sent the unindexed mnemonic, which the AGM800 refuses (ERR 24), so no set could be read or written there. Reading one into a number no longer compiles (CS0029), nor does assigning to the member (CS0200); an implementer of ISingleAxis must declare the four the same way. GantryVelGain and GantryVelKi are the velocity loop's proportional and integral gains; their documentation named the position loop.
  • The single-axis motion, homing, vector, PEG and force-control methods take double. MoveAbs, MoveRel and their AndWait / Repetitive / RepetitiveCycle / TwoSpeed variants, Jog, SetPosition, Home, HomeToHardStop, HomeToIndex, HomeToLimitThenIndex, HomeToHardStopThenIndex, SetSingleEventPEG, SetEventFixedGapPEG, SetEventTableValue, the ForceCurr_Set* family and IVector's VectorLinear / VectorArc / SetVectorParam carry their position, distance, speed, acceleration, deceleration, threshold, offset, arc-centre and gain arguments as double / double? — including the ones that were uint on the homing methods — and ForceCurr_SetForceCmdSource takes double[] for forceCurrSlope and forceCmdVal, VectorLinear params double[] pos. Millisecond timeouts and dwell times keep their integer type (uint for the homing timeouts, int elsewhere); cycle counts, directions, sources, polarities, table indices, command hold times and the vector smoothing factor (VecJerk) stay int. VecAccel / VecDecel / VecEmrgDec are float registers, so SetVectorParam(…, 1234.5, …) used to truncate on every controller, User Units or not. The same signatures change on AAMotionAPI and on the Java binding. Passing an int literal still compiles; passing an int? variable still compiles too (the nullable conversion lifts); an int[] into a widened double[] parameter does not — declare it double[]. The IGroupAxis / ICiGroupAxis CNC path builders and the IECAM table helpers are deliberately unchanged: their arguments are controller counts, unaffected by Global User Units — a CNC segment crosses as a raw SpecialBulk payload the scaling seam leaves alone, and an ECAM table is filled with the counts the controller consumes — not display values.
  • ISingleAxis.MoveAbs(dynamic position, dynamic speed = null, …) is now MoveAbs(double position, double? speed = null, double? accel = null, double? decel = null). The optional-argument call shape is unchanged: nullable value types replace the dynamic nulls rather than an overload set.
  • The multi-axis AAMotionAPI.MoveAbs / MoveRel overloads take double accel, double speed, double decel and double[] targets (double aPos, double bPos, … on the fixed-arity overloads). An int[] target array no longer binds — declare it double[].
  • ParameterTypeConverter.GetSmartValue and GetArray return double instead of dynamic, and AASmartArrayWrapper's indexer returns double. A 64-bit (long) parameter is still read with its own command rather than from the value slot; the controller's long parameters stay inside ±2^51, which a double holds exactly.
  • AAMotionConfig.UseNativeDataTypes is removed. It chose between a rounded int view and a native-type view of float/double/long parameters; the value now always arrives at full precision, so the switch has nothing left to select. Delete the assignment.
  • ParameterTypeConverter.ConvertStringToRawInt(eKeyword, string) is renamed ConvertStringToRawValue and returns double; ConvertValueForWrite(eKeyword, int) now takes a double.
  • FastReadCache.GetCachedValue / GetCachedArrayValue return double? instead of int?.
  • A multi-axis AAMotionAPI.MoveAbs / MoveRel across axes whose Global User Units differ now returns false and commands nothing. These overloads apply one speed and one accel to the vector distance over every axis, so the axes have to measure the same quantity: each must carry the same unit name in the position, velocity and acceleration groups. sqrt(dA² + dB²) over a radian and a centimetre is not a length, and the single speed the caller passes has no unit to give it — so instead of norming incommensurable deltas and running the move, the call is refused before any parameter is read from or written to the controller, and the reason arrives on MotionController.ErrorOccurred as (-1, "<method>", <message naming the axes and the group>). Different scaling factors under the same unit name still match, so two encoder resolutions on one gantry are unaffected; an axis with User Units switched off is on controller counts and does not match a scaled axis. Each axis's units come from the axis itself, so passing null as the controller does not opt out — the call still returns false, only the error event is lost — and the axes must be the SDK's own (GetAxis / AxisList): a consumer's own ISingleAxis wrapper or mock carries no axis identity, so its units cannot be checked and the call is refused. Check an axis with CommAPI.GetUserUnitsEnabled(axis) and CommAPI.MessagesContainer.TryGetUserUnitsGroup(group)?.AxisUnits(axis), or set MotionController.UseUserUnits = false to put every axis back on counts — which always matches and restores the counts-based behaviour. A machine with no Global User Units armed is unaffected.
  • A vector move across axes whose Global User Units differ now returns false and commands nothing. IVector.VectorLinear (both overloads) and VectorArc — and their AAMotionAPI equivalents — apply one VecSpeed/VecAccel/VecDecel across the whole move while each axis's AbsTrgt, and for an arc its VecArcCenter, is in that axis's own units. That only means something if the axes measure the same quantity, so the same rule the multi-axis MoveAbs/MoveRel overloads apply now covers the vector surface: every axis must carry the same unit name in the position, velocity and acceleration groups, different scaling factors under one name still match, and an axis with User Units off is on counts and does not match a scaled one. A mismatch is refused before any parameter is read from or written to the controller, and reported on MotionController.ErrorOccurred as (-1, "<method>", <message naming the axes and the group>). The profile slots are written to the axis the call was made on, which is one of the members, so it is checked as one. Set MotionController.UseUserUnits = false to put every axis back on counts, which always matches. A machine with no Global User Units armed is unaffected.
  • ISingleAxis.GantryYawRef and the eKeyword.GantryYawRef member are removed. Controller firmware deprecated the GantryYawRef keyword on 2023-11-30; every supported (post-deprecation) firmware rejects it, so the property fails against current controllers. There is no replacement — delete the calls. The sibling gantry parameters GantryFdbk and GantryOffset are unaffected.
  • ISingleAxis.ForceRelFOn / eKeyword.ForceRelFOn are renamed ForceRefFOn. The controller's mnemonic is ForceRefFOn (CAN 579); the misspelled members never resolved in the message table, so every read returned 0 and every write was rejected. Rename the call sites; the C-ABI constant becomes AAMOTION_KEYWORD_FORCE_REF_FON.
  • IIOModule.AOutGain is added beside IIOModule.AOutShifts, which is unchanged. They are two different parameters that share CAN 221 across firmware generations, not one parameter under two names. AOutShifts is an integer shift exponent — the output is scaled by 2^value — and is what firmware without float analog IO reports. AOutGain is a plain multiplier and is what firmware with it reports. So 2 means x4 on one and x2 on the other, and they are not interchangeable. Each resolves only on the firmware that carries it; on the other, reading or writing an output — AOutGain[i] with i from 1, on firmware that reports AOutShifts, or the reverse — raises IndexOutOfRangeException before anything is sent. PCSuite makes the same distinction, editing one as an integer and the other as a float.
  • IGroupAxis.CNCAEncRatio / eKeyword.CNCAEncRatio are replaced by read-only CNCACumPosRef (double). CAN 468 is the controller's CNCACumPosRef, not an encoder ratio. The C-ABI constant becomes AAMOTION_KEYWORD_CNCACUM_POS_REF.
  • MotionStat and StatReg are [Flags] enums, and ISingleAxis.MotionStatEnum / StatRegEnum return the whole register as a bit set. Every member is now the bit it names (1 << n; a None = 0 member is added), and a mirror reports every set bit — an unmapped one included — instead of the one member whose index happened to equal the register value, which mislabelled any multi-bit register (bits 1 and 2 read as the member numbered 6) and turned an unmatched value into InMotion / Commutation. Test a bit with a mask ((axis.MotionStatEnum & MotionStat.Accelerating) != 0), not with ==; code that used a member's numeric value as a bit index must use the member as the mask it now is. StatReg.StepperOpenLoopStall is bit 31, int.MinValue as an int. EnumPropertyHelper.GetStatRegDes(0) describes an empty register as "No status bits set" instead of "Commutation", bit 0's own label.
  • AAMotionAPI.ConnectSimulator, MotionController.ConnectSimulator and CommAPIInterface.ConnectSimulator (both overloads of each) are removed, together with the AllowSim and SimParamsFile user settings of AACommServer. They belonged to the file-based parameter-echo simulator that was deleted from AACommServer in June 2026; since then no shipped server could accept the connection, so every call returned false. Delete the calls. The managed firmware simulation (ChannelType.Simulation) is the replacement, and ConnectSimulation — added in this release, see Added below — is its entry point.
  • OpticalCouplingLightFinding.SpiralDir and SpiralConfig.SpiralDir are removed. They wrote AGenData[525], a spiral-direction slot the controller's light-finding process no longer defines — writing it left a value on a slot the firmware may later reuse for something else, and the direction it claimed to select had no effect. There is no replacement: delete the assignment, and drop the field from any SpiralConfig initializer. Every other spiral parameter (NumOfXAxis, NumOfYAxis, SpiralPitch, SpiralMaxRadius, SpiralAngleCoeff, SpiralScanSpeed, SpiralRtnSpeed, PowerTh) is unchanged.
  • SingleAxisConfig carries FlatZoneDecay, OptimalCoeff and FiberArrayWidth, and ApplySingleAxisConfig applies them — AGenData[509], [508] and [506], the flat-zone return gradient, the peak-versus-balance weighting and the fiber-array width. They are single-axis process parameters, so a config that leaves them at their default 0 now writes three zeros where it previously wrote nothing, which turns flat-zone return mode off rather than leaving whatever a previous run set. A caller that assigned the properties directly after applying a config should move the values into the config instead. The properties themselves are unchanged.
  • No compile error — the call now throws. HomeToIndex, HomeToLimitThenIndex and HomeToHardStopThenIndex validate their profile arguments before arming anything: a speed, acceleration or hard-stop threshold that is not a finite positive number, or a direction other than 1 or -1, raises ArgumentOutOfRangeException naming the argument, and no HomingDef slot is written. These arguments were uint before the double retype, so the type carried the non-negativity the docs state. Such a call used to return as if it had succeeded — the firmware silently rejected the out-of-range slot (its acceleration floor is 100.0 counts/s²) and the sequence ran on whatever profile the slots already held.
  • No compile error — a multi-axis call now writes nothing. WriteUserParam, UserParamWait, MultiWriteUserParam and MultiWriteUserParamWait refuse an AxisRef that does not name exactly one axis A..L: the call returns false and raises ErrorOccurred, and nothing is pushed. The segment's axis field is the port index the controller subscripts UserParam[] with, so a multi-axis mask composed a fractional field that no wire could carry. A single-axis call composes the same segment as before, with the index now an integer field.
  • No compile error — the same number now means a different duration. Homing timeouts are applied in milliseconds, the unit the API documents. Home, HomeToHardStop, HomeToIndex, HomeToLimitThenIndex and HomeToHardStopThenIndex wrote the HomingDef timeout slots as sampleRate * timeout, which treats the value as seconds — a documented 15000 ms timeout became 15000 s, so a stuck homing step effectively never gave up. The slots now carry round(timeout / 1000 * sampleRate) samples, the same conversion the PCSuite homing tool applies. A caller that compensated by passing seconds must switch to milliseconds.
  • An eKeyword member's number is an opaque identifier, not the controller's CAN code. It always was in practice — a keyword is resolved by its member name against the message table the connected controller reports, so the number never reaches the wire — but the enum documented the numbers as CAN codes and a few had drifted from any real one. A code is also product- and firmware-specific, which no single number can express: measured on three controllers, an AGM800 reports RptCounter as 732 where an AGD200 reports 714, and they agree on all 303 parameters they share. ModeSwitchPos moves to 438 and the RptMode / RptCycles / RptCounter trio to 730 / 731 / 732, the values the current AGM800 firmware uses, and PosKi is added at 714. AOutShifts moves to 2221, because 221 now names AOutGain, so a stored (eKeyword)221 means AOutGain. Managed behaviour is unchanged by all of this. A C consumer that stored the old numbers should recompile; one that treated a constant as a CAN code should read the real one from the controller with MotionController.GetKeywordCANCode.
  • MotionController.ProgHaltAll is removed. It exposed a controller command as a readable property, and reading one sends it — touching controller.ProgHaltAll.Value halted every active user program thread instead of reporting a number. ISingleAxis.ProgHaltAll() is the method that has always meant to do that, and it stays.
  • MotionController.IsConnected (and AAMotionAPI.IsConnected) no longer pings or reconnects. The getter used to actively probe the controller via ICMP on every read and, when auto-reconnect was armed, disconnect and reconnect the link on a failed probe — a property read could block for up to ~19 s, and a debugger watch window or a WPF binding could disconnect a healthy controller just by evaluating it. The getter is now a cheap, non-blocking read of the comm layer's own logical connection state. Call the new MotionController.CheckConnection() / AAMotionAPI.CheckConnection(controller) to actively probe reachability, and TryReconnect to recover a link that is actually down. enableAutoReconnect (Connect's parameter, AutoReconnectEnabled) is recorded but no longer has any automatic effect.
  • A typed read that fails now throws ControllerCommandException instead of answering 0. A parameter read through a typed property, through one of the Is* status helpers built on them, or through MotionController.GetValue, used to answer 0 when the controller refused the read or replied with something that is not a number — indistinguishable from the controller genuinely reporting 0, which is what a position, a velocity and a status word all report at rest. The exception carries the controller's own error code, the keyword and the exact command text. No signature changes, so the compiler reports nothing: a poll loop that read a status property over a dead link used to spin on an invented 0 and now leaves the loop at the first failed read. ISingleAxis.TryRead, ISingleAxis.TryReadArray and MotionController.TryGetValue are unchanged — they report the same failure as false and never throw — and LastReadError and ReadFailures record the failure on both routes, throwing and reporting alike. An AADoubleArray element read, such as MotionController.GenDataD[i], a direct ParameterTypeConverter.GetDoubleArray call, and the raw register reads ReadGenDataF, ReadGenDataD, ReadUserParam, ReadUserParamF and ReadUserParamD on MotionController and AAMotionAPI follow the same contract; they used to raise InvalidOperationException or FormatException, record nothing, and hand back a NaN or infinite reply as a value. A consumer catching InvalidOperationException around a GenDataD[i] or other AADoubleArray element read, FormatException / InvalidOperationException around a ParameterTypeConverter.GetDoubleArray call, or FormatException around one of those five register reads, must catch ControllerCommandException instead. Nothing new crosses the C ABI: every export already turns a managed throw into its failure status, so aamotion_get_value now reports false for a reply that is not a number where it used to hand back 0 as if it had been read.
  • A typed set the controller refuses now throws ControllerCommandException instead of doing nothing. Assigning to a typed property — axis.Speed = 1000, axis.AbsTrgt, axis.Vel[1], controller.GenData[3] — used to discard the controller's answer, so a refused write left the parameter holding its old value with nothing at the call site to say so, and only a subscriber to ErrorOccurred ever heard about it. The exception carries the controller's own error code, the keyword, and the exact command text including the assignment (ASpeed=1000), so the failure names the value that did not take. No signature changes, so the compiler reports nothing. The consequence to plan for is that a call which writes several parameters before it commands anything — MoveAbs, MoveRel, ConfigureSlowLogger — now stops at the first refusal instead of running to the end, so an axis no longer begins on a profile the controller never took. The optical-coupling configuration is the exception and is unchanged: its properties assign through MotionController.WriteGenData, which catches the refusal into a false the setters discard, so it still runs to the end and still reports through ErrorOccurred once per refused slot. MotionController.WriteGenData reports a refused slot write as false, which is what its documented contract always promised. A failed write is deliberately NOT recorded in LastReadError and NOT counted by ReadFailures — both are the read record, by name and by their own documentation, so a consumer polling them for stale reads keeps being told about reads and nothing else. There is no TrySet: catch the exception, or keep using ErrorOccurred, which is still raised for every refusal. The two array paths that reach the controller through AASmartArrayWrapper's setter rather than the changed-value event — a long-typed array element, and MotionController.GenDataD — raise the same type as everything else: they used to raise InvalidOperationException with a message carrying no error code, so catch (ControllerCommandException) missed them and the payload was reachable only as text. A consumer catching InvalidOperationException around a GenDataD[i] or long-array element write must catch ControllerCommandException instead. Nothing new crosses the C ABI — every write export already turns a managed throw into its failure status, and the status bytes are unchanged.
  • No compile error — .Value on an array member now throws. An array parameter has no single value. On any AAValueArray<double> member — MotionController.GenData, IIOModule.AInMode, ISingleAxis.HomingDef and the rest — whose parameter the connected controller lists as an array of one or more elements, .Value raises InvalidOperationException on get and on set, before anything is sent, with a message naming the parameter and the indexes it has (AInMode is an array parameter; read an element from index 1 to 4.). The getter used to answer the slot's cached first element without reading the controller — 0 before any element was read — and the setter sent nothing, so a write was dropped and the next .Value handed it back as though the controller held it. ParameterTypeConverter.GetSmartValue and SetSmartValue go through .Value, so they throw the same for such a keyword, except a 64-bit (long) one, which they still send unindexed with its own command; the controller refuses that (ERR 24), raised as ControllerCommandException. Read or write an element by its index instead, from StartIndex to EndIndex: io.AInMode[1], or MotionController.GetValue(axis, keyword, index), which already refused index 0 on an array parameter. Nothing crosses the C ABI: aamotion_get_value reads through GetValue.
  • IGroupAxis.IsCNCCompleted raises ControllerCommandException on a failed status read, on both groups. It is a poll-until-flips predicate, and a predicate has no answer for a link that did not reply, so it now raises rather than reporting a completion state it could not read. The Group B branch previously returned false, which left a while (!IsCNCCompleted(...)) loop spinning forever on a dead link; Group A already raised, because it reads through the value-answering path that 12.0.0 made throw. Wrap the poll, or read the status yourself with TryGetValue if a failed poll is an expected outcome. The C ABI is unchanged — aamotion_is_cnc_completed already caught and returned 0 either way. The Wait* family is deliberately untouched: a wait returns whether it succeeded, and a failed read means it did not, which is the abort behaviour 12.0.0 already introduced.

Added

  • Add MotionController.CreateEventTableClient(axis) for the shared explicit verified-table lifecycle; it does not commission, move or automatically arm an axis.
  • AAMotionAPI.DownloadParameters orders the lock/event writes for firmware with the LockEventMode 1/2 guards (Firmware-Main #1256). On such firmware the controller refuses a change to EncSinCosHWEn, EncDir, VEncSrc or VEncOn (and AuxEncDir with the aux source, VEncFact/VEncFactDen with the VEnc source) while LockEn or EventOn is on (ERR 403), and refuses LockEn/EventOn with a stale offset (ERR 404; ERR 335 still means LockEventInit never ran). A .par is written in file order, so a restore over an armed axis, or one that re-arms after changing the source, failed partway. When the controller's firmware has the guards (it declares LockEventMode up to 2) and an axis's rows touch a dependency or LockEventMode, the download now writes LockEn and EventOn = 0 first (a .par carries neither, as they are not flash parameters, so the restore leaves that axis's Lock and Event off), then the other rows in file order, then LockEventMode, then LockEventInit when the axis is in mode 1 at re-arm (the file's LockEventMode row, else the controller's current mode, which the download reads first; if that read fails nothing is written), then the file's own LockEn/EventOn rows in file order, so the last one requested is the state left. The axis letter is matched case-insensitively (a and A are one axis). The added rows are sent but not counted as written. A refused disarm counts in ErrorCount, is listed in Rejections marked as added, fails the download with a completion error, and nothing is committed. A refused LockEventInit (ERR 151 when the remote can't be reached, say) counts in ErrorCount and is listed in Rejections, marked to be run before enabling Lock or Event, and the download still commits: the firmware refuses to arm that axis (ERR 335 or 404) until LockEventInit succeeds. Firmware that declares LockEventMode only up to 1 has no such guards and is written in file order. Integrators who write these keywords themselves need the same order; EncFilt, AuxEncFilt and CurrDir are not dependencies.
  • AGM800-EC: DownloadParameters treats the drive like any other until its next enable (Firmware-Main #1258). The drive's EtherCAT enable forces LockEventMode 2 and learns the offset itself, but only at that enable, so a restore that leaves the axis in mode 1 still runs LockEventInit before re-arming. The disarm still comes first. On EtherCAT it also drops an armed touch probe, which the master re-arms by toggling the 0x60B8 enable bit.
  • MotionController.UserProgramPrintReceived / AAMotionAPI.SetUserProgramPrintHandler / ClearUserProgramPrintHandler — subscribe to user-program printf lines (FW v5+, AGM800 Ethernet) as UserProgramPrintMessage. Wire fields: TimeSec, TimeTick, Thread, Message. Console-friendly fields: Timestamp (wall clock from ATime boot + stamp at the current-loop sample rate) and DisplayText (strips a leading !R!/!G!/!Y!, trims trailing CR/LF, expands literal \n/\r/\t). ATime is queried once (async CommAPI.Send, same path as the PCSuite Console — not sync SendReceive, so a clock timeout cannot tear down a fresh connect) when the first handler is added while connected, or on connect / a successful TryReconnect that rebuilt the link when a handler is already subscribed; the first printf line seeds the boot if that query fails. Disconnect/Dispose stop delivery so a late push cannot reseed the clock; TryReconnect reopens delivery after a disconnect. Clearing a handler mid-packet stops further lines in that packet. Typical Console use: Console.WriteLine($"{m.Timestamp:yyyy-MM-dd HH:mm:ss.fff} [T{m.Thread}] {m.DisplayText}"). Delivery rides the existing AAComm push path (CommAPI.OnPushMessageReceived → AACommPushMsgUP); no second socket on port 50010. Other push sources are ignored.
  • ControllerCommandException — the exception a failed command raises, and the only one AAMotion defines. It carries ErrorCode (the controller's own code, or NoControllerCode when the SDK detected the failure itself — a reply that is not a number), Keyword, Command (the exact text that was sent, array subscript and assigned value included) and a Message composed from all three, so the one line a user pastes into a bug report names the command as well as the error.
  • MotionController.ConnectSimulation / AAMotionAPI.ConnectSimulation(controller, simExePath[, …]) — the managed firmware-simulation entry point over ChannelType.Simulation (#902). Pass the absolute path to a firmware_sim.exe on disk — a relative path is refused, because the SDK checks it against the calling process's working directory while AACommServer spawns it from its own, so a relative path that looks valid here can name a different file there. AACommServer spawns it, configures the motor, and bridges loopback. The SDK does not ship the binary and does not read a sibling sim.info — optional simProduct, simVersion and simMotorProfile parameters are forwarded when supplied. A simProduct the product catalog knows also declares the controller type (AGM800, AGD155, AGD155-EC, AGD101-EC, AGD156-EC, DRV6-V3, Pulse-Sync, AGM800-EC, AGD301, AGC301, AGD200, AGC300, the paired spellings AGD301orAGC301 and AGD200orAGC300, the deprecated AGM400, and the older spellings of the ones that have them), which roughly halves the connect: discovering it instead costs a probe that spawns and reaps a whole extra firmware_sim child before the session's own. A declared type is verified like any other connection's, so a simProduct that disagrees with what the sim reports fails the connect — ConnectSimulation returns false, and the underlying InvalidControllerType appears in the AAComm debug log — instead of connecting to whatever the sim actually is. A name the catalog does not resolve is discovered by that probe, exactly as omitting it is — among them the four EtherCAT ControllerType member names (AGD155EC is catalogued AGD155-EC). Disconnect reaps the child process. TryReconnect remains Ethernet-only. Changed

  • The digital-output bit API states its index conventions. DOutSetBit / DOutClearBit / DOutToggleBit and the group and Central-I twins take the 1-based output number the controller's DOutPortSBit[n] takes; GetDOutPort / GetDInPort read a 0-based register bit, so output n is GetDOutPort(n - 1). Documentation only — no member changes behavior.
  • A write carries the caller's value whole to AAComm, which divides it by the User Units factor and rounds a firmware-integral parameter in controller counts. AAMotion used to narrow the display value first — to an int for a 32-bit parameter, to a long for a 64-bit one — which quantised a scaled axis to whole units: at 0.01 mm/count, axis.AbsTrgt = 12.345 reached the controller as 1200 counts instead of 1234. The two setter families also disagreed, so the same fraction was rounded on AbsTrgt and passed through raw on MaxVBus. Both now behave the same, and the rounding — to-even, on the counts — happens once, in AAComm's transmit seam. An integral 64-bit assignment still crosses with its exact digits, so a .par round-trip above 2^53 is unaffected.
  • The commands that render a value straight into their command text — ISingleAxis.SetPosition, SetEventTableValue, and the VectorLinear / VectorArc target and arc-centre writes — render it with the invariant wire format. They were culture-safe only for as long as those arguments were int.
  • Connecting no longer retries with forced About data; a failed connect fails on the first attempt (AAComm now refreshes a stale About cache itself). The same applies to the auto-reconnect path.

Fixed

  • A .par for another product is refused. DownloadParameters read no product from the file, so a .par taken from an AGD200 wrote onto an AGM800. When the file's // Controller type: header names a product other than the connected controller's, nothing is sent and the completion callback gets an error naming both products. The controller's legacy names (AG300-CTL02 for an AGD301, say) and the name UploadParameters writes for it are accepted; a header name no product answers to is refused the same way, and a file with no header downloads as before.
  • An integer keyword takes the rounded value on every transport. DownloadParameters sent an integer keyword's 123.5 as 124 over Ethernet, where AAComm's binary form rounds it, and as text over RS-232, where firmware refuses a value with a fraction or an exponent. It now rewrites the value of an integer keyword that is not already an integer literal to the integer firmware's own rounding gives (half away from zero: 124.5 is 125, -2.5 is -3) before it is checked or sent, so both carry the same integer for a value within the keyword's range. A float keyword's value is sent as written.
  • Every row a parameter download skips is named. A line the reader dropped (no =, under 3 characters, an axis outside A-L) was neither counted nor named, and a row the connected controller does not support and the ProductSN row were counted in SkippedCount without a Rejections entry. Each now has an entry with a PC Suite: ERR reason and counts in TotalCount; they are the first SkippedCount entries of Rejections. aacomm.cli params-download prints every one as skipped <row> -> <reason>.
  • Two FastReadCache refreshes can no longer run at once. The cache read its in-progress flag and set it a line later, so a RefreshNow() and the refresh timer arriving together both got through: two bulk reads went out on one connection, RefreshStarted fired twice for the one refresh a caller expected, and both completions re-armed the timer. The flag is now claimed in a single atomic step and freed on every way out of the refresh — including a RefreshStarted handler that throws, which used to leave the cache refusing every later refresh for the life of the process; such a throw is now reported on RefreshError like any other refresh failure. IsRefreshing is unchanged.
  • A FastReadCache whose RefreshCompleted handler throws keeps refreshing. The refresh raised RefreshCompleted before it scheduled the next one, and the refresh timer fires once per schedule, so a throwing handler stopped the periodic refresh for good: IsRefreshing read false, no error was raised, and readers kept getting the last values read. The next refresh is now scheduled first, and the handler's exception is reported on RefreshError, as a RefreshStarted handler's already was; RefreshNow() no longer throws it at the caller. Because the next refresh is already scheduled, it can start before a slow RefreshCompleted handler returns.
  • A throwing UploadParameters / DownloadParameters completion callback is called once. A callback that threw was called again with its own exception ("Exception in upload completion: …", "Upload failed: …", "Failed reading .par file: …", "Exception in download completion: …"), and an upload then counted its rows a second time and wrote the .par again, reporting doubled SuccessCount / ErrorCount. Each upload and download now calls the callback exactly once, whatever the callback does; its exception is not reported back to it.
  • A parameter upload or download that stops partway reports the failure and saves nothing. When the bulk run ended with an error after some replies had arrived (a throwing onProgress callback is one way), UploadParameters reported success and wrote the .par with empty values for every row it never read, and DownloadParameters counted the unsent rows as written and, with calcAndSave, saved the partial transfer to flash. Both now report the run's error: the upload writes no file, and the download counts only the rows that were answered, never sends ASave / CalcFilters for a partial transfer, still resyncs User Units, and reports no final 100% progress. A throwing onProgress on the download's final 100% no longer leaves onDone uncalled: the exception's message is appended to the reported error.
  • A parameter download that fails before its first message reaches the wire now reports the failure. The bulk runner behind DownloadParameters reads the connection's bulk size and connected state at the start of a transfer, and an exception from either escaped onto the background task driving the download — OnDone never fired and the call went quiet. Both reads are now covered and the failure arrives on OnDone with the exception's message, and a download whose transfer sent nothing no longer reports every parameter as written: the completion treated an empty reply set as a clean sweep, counted the whole file as successful and then committed it to flash with ASave. It now reports the failure and commits nothing, as the upload path already did. The runner's one-at-a-time start guard is claimed atomically as well, so two starts on one runner cannot both proceed.
  • MotionController.EnsureAACommServerRunning(serverExePath) starts the server through the same contract every other entry point uses, and answers on the port. It span its own process and judged “running” by the process list, so it missed --headless, the hidden window, the zone-check opt-out that keeps a Mark-of-the-Web executable from stopping on a modal security prompt, the lock that serialises two spawns, and the readiness poll that notices a child which died on startup; it also answered true for a process that had not bound its port yet, and never recognised a running AACommServerNative. It now delegates to CommAPI.StartAACommServer and reports whether a server is serving. A null or empty path starts nothing and reports whether one is already serving — delegating it would auto-locate and could start the machine-wide install the caller never named. The signature and the bool contract are unchanged.
  • TryReconnect no longer tears down a healthy link on a single flaky ping. Its "already connected and reachable" check sent one ICMP probe; a switch or firewall that blocks or rate-limits ICMP could make a live link look dead and trigger an unnecessary disconnect/reconnect cycle. Two independent probes are now sent, and either succeeding is treated as reachable.
  • A parameter download no longer moves the controller off its own network address. DownloadParameters wrote EthernetIP and EthernetMAC like any other row, so a .par taken from one bench and written to another re-addressed the target controller and the operator lost it mid-restore. Both are the controller's identity rather than part of its configuration, so the download now withholds them whatever the file carries — the same pair PCSuite's Parameters Download window excludes. A withheld row counts as skipped, not as a failure, and is listed in ParamHandlingSummary.Rejections with a client-side reply naming the exclusion, so nothing is dropped silently. EthernetPort is not identity and is still written.
  • A parameter file round-trips: what a controller uploads, it accepts back. A .par holds raw controller values, but the transfer applied Global User Units scaling on the way out and could not write the User Units configuration rows at all — *UnitFct / *UnitUnt[] are refused over raw messaging, which is 1068 of the 1106 rejections a full AGM800 download still reported. Both legs now carry raw values and are permitted to write that configuration, and the scaling cache is resynced afterwards, which is the contract for that bypass. Measured on an AGM800: a self-produced .par downloads back with 36 rejections where it had 4110, and those 36 are a firmware defect fixed in FW 5.2.1.16-3 rather than anything the SDK does.
  • Keywords the firmware refuses to carry inside a bulk packet (ERR 184 — UserUnitsEn is one of a set) are re-sent one at a time after the batched pass, instead of being reported as rejections. The retry keys on the reply, so it covers every keyword in that set rather than a list that goes stale.
  • ProductSN is no longer attempted by a download. It is writable only with elevated permission and answers ERR 328 otherwise, so it counts as skipped — the same class the connected controller does not support — rather than as a failure.
  • A parameter download no longer abandons the rest of a bulk packet at the first refused row. DownloadParameters batches up to 50 assignments per packet, and a plain bulk packet stops executing at its first error — so one row the controller refused silently discarded up to 49 writes behind it, and the unanswered tail was counted as a rejection per slot. A full .par download reported thousands of errors where only a few rows were genuinely refused, and the parameters that never reached the controller were not reported at all. Both legs now use the continue-on-error bulk packet, so every assignment is attempted and every reply is the controller's own. Firmware that does not implement that packet kind (it answers ERR 160) is detected on the first batch and the transfer falls back to the previous behaviour.
  • A .par saved by UploadParameters names the controller by product name. The header's // Controller type: line carried a hex product id (0xA for an AGM800), which PCSuite's Parameters Download cannot resolve, so it skipped the Central-i master / standalone mismatch warning for every file AAMotion wrote. The line now carries the product name PCSuite writes there for every controller it supports, so that warning applies to AAMotion's files as it does to PCSuite's own.
  • A parameter download with calcAndSave — the default — commits to flash. DownloadParameters is meant to finish with ASave and a CalcFilters per axis, and it sent neither: the commit ran on the transfer's reply callback, where AAComm refuses a synchronous send, and looked for CalcFilters under an axis-prefixed name the message table never carries. The completion callback still reported success, so every parameter the download wrote was gone after the next power cycle. The commit now runs off that callback, and a failure in it arrives in onDone's error argument instead of being dropped.
  • The DataLogger CSV export (GenerateCsvFile) is readable on a comma-decimal host: every time, value and statistics field is written with a dot decimal separator. It rendered under the host culture, so on de-DE, fr-FR and similar locales each fractional value became two columns and no reader could recover the rows.
  • ConfigureSlowLogger accepts the documented forty parameters and clears the fortieth slot. LoggerParams is a 1-based table, and the configure walked it as if it were 0-based: the fortieth parameter was refused as a forty-first, and a stale code left in slot 40 by an earlier configuration kept being logged.
  • ConfigureSlowLogger refuses an array parameter given without its index, and an index given on a scalar, with an ArgumentException and one ErrorOccurred — the fast recorder's verdicts, on all three specification shapes (string, CAN code, SlowLoggerParameter). An un-indexed array used to be accepted and logged nothing.
  • Every vector entry point — VectorLinear (both overloads), VectorArc and their AAMotionAPI equivalents — refuses a call whose initiating axis is not a member of the move, or not its lowest member, before anything is written: the call returns false and raises ErrorOccurred. The controller reads the profile from the axis that receives Begin and rejects any other shape (errors 192 and 266), so b.VectorArc(C, H, …) never ran; it used to leave the profile and the members' targets on the controller before the controller refused Begin.
  • VectorLinear (both overloads) and VectorArc refuse a move that names an axis past H or fewer than two members, before anything is written. The controller's VecMemberAxes reaches H and a vector move needs two members (error 196), so such a call never ran; the refusal is now local and reported.
  • VectorLinear (mask overload) refuses a position array shorter than the mask's axis count before the first write. It used to notice the missing position only when its walk reached that axis, after the profile and the earlier axes — motors on — were already on the controller.
  • The four-axis Central-I LinearAbsolute(aPos, bPos, cPos, dPos, velCruise, velEnd) now sends the D position. It named D in the segment header but composed only three positions, so the controller refused every call with ERR 181 and no such move ever ran. ArcXT / ArcYT / ArcZT had the same slip - nine fields where the arc row takes ten - and are corrected with it.
  • GenDataWait and UserParamWait now push the wait-array segment type (12). They carried the write type (9) with a wait body, which the controller refuses with ERR 181 before pushing anything; the field order was already the wait segment's, so the arguments are unchanged.
  • Position-class values no longer read back as 0 on a controller with User Units enabled — the 64-bit parameters Pos and PosRef, which are re-read from the controller by their own path, included. A scaled reply for an integral parameter is a decimal number (2468 counts at a 0.01 mm/count factor is 24.68), and the client parsed every reply as an integer — 24.68 failed to parse and the value became 0, so a.Pos read zero and any move computed from it went to the wrong place. Replies are now read as decimal numbers and carried at full precision, so a User-Units axis reports its real position. An integration that wants the raw controller counts instead can opt out per controller with the new MotionController.UseUserUnits: set it to false at any point, before or after Connect, and the controller keeps it across connects and reconnects. The opt-out is instance-wide (two controllers sharing one CommAPI share it) and does not unlock raw *UnitFct / *UnitUnt writes. ISingleAxis.SetPosition sits outside the scaling: it writes a parameter the controller declares unscaled, so its argument is always in controller counts — SetPosition(axis.Pos) is not a round trip on a scaled axis; divide the display value by the axis position factor, or read the position with UseUserUnits = false and pass that count back.
  • Float- and double-typed parameters no longer come back as a re-interpreted bit pattern. ForceGain, ForceKi, ForceKd and their siblings return the value the controller reports, and writing one sends that value rather than the integer its bits happen to spell. The write is spelled as the shortest invariant text that reads back as the same value, so it no longer loses digits on .NET Framework, and the same value is spelled identically on every framework.
  • Multi-axis AAMotionAPI.MoveAbs / MoveRel no longer command Speed = 0 — a move that silently never runs — when a requested component speed exceeds an axis's MaxVel. The profile clamp divided two int operands, so the quotient truncated to zero and every axis was scaled to a standstill; where it did not truncate to zero it still dropped the fraction and under-drove the whole move. The profile is now computed in double precision, with one shared scaling factor equal to the tightest axis constraint, preserving the equal-duration (PTP) relation between the axes. The same clamp turned the shared factor negative when the constraining axis travelled backwards, commanding a negative speed on the axes travelling forwards; the factor is now always a magnitude. Accel / Decel were scaled by the same clamp and are corrected with it.
  • Multi-axis AAMotionAPI.MoveAbs / MoveRel no longer command a negative Speed, Accel and Decel on an axis travelling backwards. Each axis was written its signed component of the profile, so the controller rejected that axis's Accel/Decel with ERR 14 ("Assigned value out of the range defined for this keyword" — the keyword minimum is 100.0) and ran the move on whatever acceleration profile the axis happened to hold; the negative Speed, which the controller does accept, persisted as an axis parameter and then drove the next move on that axis that supplied no speed of its own — MoveAbs / MoveRel write Speed only when the argument is given, while Jog always writes its own. Every axis is now commanded the magnitude of its component — direction comes from the target position, as before.
  • Multi-axis AAMotionAPI.MoveRel no longer overwrites the caller's distance array with the absolute positions it computes. The array passed in is left untouched, so a caller that reuses it for a second move is no longer silently moving to the wrong place.
  • MotionController.ReadGenDataF / ReadGenDataD and ReadUserParamF / ReadUserParamD now read the controller's reply in the invariant culture. The single-argument float.Parse / double.Parse they used applied the process culture with its default styles — which accept a group separator, and on a comma-decimal locale that separator is . — so a reply of 1.5 came back as 15, a tenfold-wrong reading with no error. They now parse invariantly, matching the text AAComm emits.
  • MotionController.WriteGenDataF / WriteGenDataD and WriteUserParam / WriteUserParamF / WriteUserParamD now render the value they send in the invariant culture. They formatted it with the process culture, so on a comma-decimal locale WriteGenDataF(1, 0.25f) sent AGenDataF[1] = 0,25 — and because the controller reads an assignment invariantly and accepts a group separator, the slot silently ended up holding 25. The command was never rejected, so the wrong value went unnoticed; the slot now receives the value that was passed in, on every locale.
  • Multi-axis AAMotionAPI.MoveRel no longer truncates the axis's position reference when it converts a relative move to absolute. It accumulated aryTrg_Pos[i] + (int)aryAxes[i].PosRef into an int array, so a fractional PosRef — what a User-Units axis reports — was dropped before the target was computed and the move landed short by up to one unit. The conversion is now done in double.
  • Homing speeds, accelerations, offsets and thresholds are no longer truncated on their way into HomingDef. Home, HomeToHardStop, HomeToIndex, HomeToLimitThenIndex and HomeToHardStopThenIndex cast every profile argument to int before writing its slot; they now carry it whole.
  • ISingleAxis.Home(string filePath) reads the homing-definition file's values as decimal numbers. It parsed each HomingDef[i] = value line with an integer parse, so a fractional speed or acceleration in the file was skipped silently and the slot kept whatever it already held.
  • The ECAM table generators apply the requested range before they push the points, so a generated table lands at the startIndex the caller asked for. ECAM_CreateLinearTable and ECAM_CreateSinusoidalTable called ECAM_SetTableData first, and that method takes both its destination and its length cap from the range in force at the time — so on a table that had never been ranged the push failed with an IndexOutOfRangeException before a single point reached the controller, and on a table reused from an earlier profile the points landed at the previous start index, truncated to the previous length, under a range the data never filled.
  • ECAM_SetTableData writes the last point of a range that ends at the final GenData slot. Its loop was bounded by the array's element count on a 1-based array, so the highest slot was silently skipped — a table configured as 1022..1024 on a controller whose GenData ends at 1024 arrived one point short. A range that starts below GenData's first index is now rejected without writing anything, instead of throwing IndexOutOfRangeException on its first slot.
  • ECAM_CreateSinusoidalTable closes the sweep at any offset. The closing sample was computed from sin(2π), a tiny negative residue rather than zero, so with a non-zero offset the cast landed the last point one below the first — amplitude 1000, offset 500 over 5 points ended on 499 instead of 500 — and the cam profile stepped at the seam on every cycle. The closing sample is now the opening one exactly.
  • OpticalCouplingLightFinding.GetSingleAxisScanResult now returns the per-channel peak indices. SingleAxisScanResult.ChannelPeakPowerIndices was never filled, so it came back as null — a NullReferenceException for a caller reading it alongside the peak powers and positions it sits with. It now carries channels 1-4, from the same slots the Channel1..4PeakPowerIndex properties read.
  • The per-axis IO register reads keep the controller's bit pattern when bit 31 is set. IIOModule.DInPort, DInPortHigh, DInLog, DInLogHigh, DInFilt, DOutLog, DOutType, DOutPort and BiDirConfig narrowed the value slot with a plain cast, so a register reported as an unsigned full-width word — 4294967295, every output asserted — read back as -2147483648 on .NET Framework and .NET 8 and as 2147483647 on .NET 10, none of which is the register the controller holds. They now take the same 32-bit two's-complement view the group DOut bit helpers use, which is identical on every framework.
  • The analog outputs can be read and written again, one element per output. IIOModule.AOutGain, AOutShifts, AOutOffset, AOutMode and AOutPort were not sized from the controller's parameter table, so every element access — io.AOutGain[i] for any output, read or written, or MotionController.GetValue on one of them — threw IndexOutOfRangeException before anything was sent. AOutGain[i] reads and writes the i-th analog output, from 1 to the count the controller reports; read an output by its index, because on a controller that lists that parameter with one or more outputs the member's own .Value raises InvalidOperationException, as on every array member. A drive without analog outputs (AGD101-EC, AGD156-EC) lists these parameters with no elements; it connects as before, and reading or writing an output there raises IndexOutOfRangeException with nothing sent.
  • An array parameter the controller lists with a single element can be read and written. A parameter at max index 1 was sized as a scalar, so its element 1 threw (NullReferenceException, or InvalidOperationException through IIOModule.AInGain) and a write to it returned normally and sent nothing, losing the value. It is an array of one element, read and written as element 1 like any other array, and GetValue(axis, keyword, 1) reads it. The AGD200 (3.0.33) and AGD155-EC (1.5.0.20) tables list ISingleAxis.PosFiltOn and MapTableB to MapTableE this way, and the AGD101-EC and AGD156-EC can list the analog inputs so (IIOModule.AInGain, AInMode, AInFilt, AInOffSet, AInDB).
  • An element of a scalar parameter is refused instead of lost. On an AAValueArray<double> member whose parameter the connected controller lists as a scalar, such as ISingleAxis.GantryPosGain on an AGD200, its one index [0] and enumerating the member raise InvalidOperationException before anything is sent, naming the parameter (GantryPosGain is a scalar parameter; read it through Value.). A read of [0] used to raise NullReferenceException, and a write returned normally and sent nothing, and enumerating the member then handed the value back as though the controller held it. Read and write such a parameter through .Value.
  • An element of a 64-bit array parameter is read once. MotionController.GetValue(axis, keyword, index), and with it aamotion_get_value, composed the element read through the parameter slot and then again through the 64-bit path, so a successful read of an element of Vel, MapStartPos, ModeSwitchPos, ECAMMasterIni or CNCBVel — the 64-bit arrays the client sizes from the AGM800's table — cost two round trips instead of one. ISingleAxis.Vel[i] reads through that same path and doubled with it; the other four are read once through their own members. The value is unchanged, and so are the refusals: an index the parameter does not have is still refused before anything is sent.
  • MotionController.GetValue(axis, keyword, index) reads an element of the arrays the AGM800 lists for GantryPosGain, GantryAccFFW, GantryVelGain, GantryVelKi and PosKi (to 5), GenDataF (to 100), UserParamF and UserParamD (to 20). They were sized as scalars, so an element read raised IndexOutOfRangeException before anything was sent, while TryGetValue read it.
  • The CNC segment builders no longer corrupt a segment on a comma-decimal locale. IGroupAxis.SetMotionProfile's S-factor, and the axis index the WriteUserParam / UserParamWait / MultiWriteUserParam / MultiWriteUserParamWait builders derive from the AxisRef they are given, were rendered under the process culture; on de-DE, fr-FR or ru-RU the decimal comma became an extra separator inside the comma-delimited segment and shifted every field behind it into the wrong slot. Both now render in the invariant wire format, so a segment is spelled identically on every host.
  • Reading a controller command as though it were a parameter no longer runs it. ProgRun, ProgHalt, ProgHaltAll, ProgReset, StopECAM and LoggerUpload name functions the controller performs on receipt, not storage slots — so composing a read of one is the command: ParameterTypeConverter.GetSmartValue(axis, …, eKeyword.ProgRun) started the user program and reported its reply as a value, GetDoubleArray(axis, …, "ProgHalt", 1) sent AProgHalt[1] and halted user-program thread 1, and MotionController.RegisterCacheKeywords(axis, eKeyword.ProgRun) put the command in the fast-read cache's refresh bulk, re-sending it every millisecond for as long as the cache ran. All six are now refused with an ArgumentException on GetSmartValue, GetArray and GetDoubleArray — which covers the protected Node.GetSmartValue a derived controller inherits — and on RegisterCacheKeywords / FastReadCache.RegisterArrayElements, before anything reaches the wire; a registration naming one is refused whole, so no keyword beside it is registered. MotionController.GetValue already refused them. This is not a rule that a command never answers with data: many controller commands take a parameter and reply with a value, and MotionController.LoggerUpload() — which retrieves the slow-logger data by sending ALoggerUpload itself — is unaffected.
  • Expanding a MotionController, an axis or a parameter array in the debugger no longer hangs the evaluation. Every value property on them is a controller round trip, so a debugger expanding one sent a read per member while it held frozen the thread that delivers the reply, and hung on the first. The debugger now shows their identity only — the kind and axis, a controller's last known address, an array's keyword and index range — and sends nothing to the controller.

Removed

  • The MotionController.ProgHaltAll property. It exposed the ProgHaltAll command as a readable value slot, so evaluating it — in code, or in a debugger watch expanding the controller — sent AProgHaltAll and halted every user program. Halt them deliberately with ISingleAxis.ProgHaltAll() or AAMotionAPI.ProgHaltAll(controller, axis), which are unchanged.

The native aamotion SDK's Release/Disconnect likewise no longer shut the server down — the explicit Shutdown export is the only path that may.
  • Enabling the fast-read cache no longer risks tearing down the connection when any call slower than ~200 ms is in flight — the background cache refresh used a hardcoded 100 ms timeout, tighter than any other command's wire budget; it now uses the default message timeout (a slow reply just delays the next refresh while readers serve the cached value).

Disconnect invalidates all entries (no unbounded-stale values while no refresh can run) and the background refresh no-ops while disconnected instead of spamming an error event per interval — throttled to an idle poll (500 ms) so a 1 ms-interval cache no longer burns ~1000 no-op tasks per second while disconnected; it resumes the configured cadence by itself after a reconnect.

  • UploadParameters() / DownloadParameters() summaries no longer count API-synthesized error replies (PC Suite: ERR …, BOOT … ERR, e.g. from a connection lost mid-transfer) as successes — error classification now matches the full AAComm reply taxonomy instead of only controller ERR … replies.

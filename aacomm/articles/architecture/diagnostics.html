Diagnostic Debug Logs — client, server, and how they join

The SDK's always-on diagnostic layer: what the AAComm client and AACommServer record about session lifecycle, where the files land, and the procedure that correlates the two logs for a single connection. This is the spec for the diagnostic logs only — the AACommServer comm log (per-channel message traffic, saved from the server UI) and PCSuite's Serilog session log (the PCSuite_DebugLogs sibling) are separate facilities.

Design constraints

  • Zero-config, always-on. AAComm runs inside customer processes; a diagnostic that must be enabled first never exists when the incident happens.
  • Zero steady-state file IO. Entries accumulate in an in-memory ring; a healthy process never touches the disk. Only a severe event (or an explicit flush) writes a file.
  • No per-message traffic. Message-level logging is the AACommServer comm log's job; the SendReceive/Send hot paths gain no logging on the success path.
  • No wire change. The client↔server correlation works purely from what each side already sees on its own socket.

Folder layout

One folder per producer, all under %LocalAppData%\PCSuite\:

Folder Producer Written when
AAComm_DebugLogs\ AAComm client (AACommDebugLog) severe event or Flush()
AACommServer_DebugLogs\ AACommServer (GlobalLogger); sniffer captures under Sniffer\ shutdown save, flush verb, implicit-shutdown save
PCSuite_DebugLogs\ PCSuite exes (Serilog session log) continuously (buffered)

All debug-log folders prune independently on a file-count cap of 200; when a save finds the folder over the cap, the oldest files are deleted down to the newest 100 (half the cap), so the prune fires rarely rather than on every save.

Local application data — not Documents — is deliberate: Documents redirects to OneDrive, whose sync locks capture files and contends with snapshot IO under connect/close churn.

Client log — AAComm.Services.Diagnostics.AACommDebugLog

Static, process-wide, shared by every CommAPI instance in the process.

Line format and identity tags

HH:mm:ss.fff [api#N/conn#M] text
  • api#N — the CommAPI instance, numbered in construction order (assigned in the designated constructor every overload funnels into).
  • conn#M — that instance's successive successful channel opens. Before the first open the tag is just api#N.
  • The connect line is the one line whose tag also carries the endpoint: [api#1/conn#1→Ethernet 172.1.1.101:5000]. Every later line is tag-only, so a reader greps the endpoint once and then follows the short tag.
  • The ring's first entry is a one-time header: === AAComm diagnostic log — process <name> (PID <pid>), path <exe path>, AAComm <version>, started <timestamp> ===

Flush-on-severity

A library in the customer's process has no reliable exit hook, so severity is the flush trigger. Ring: 10 000 entries, oldest 10 % evicted on overflow.

  • Triggers: sync phase-2 teardown (SyncTimeout), FATAL / comms error (Fatal), and the public on-demand AACommDebugLog.Flush() (Flush, synchronous).
  • File: {yyyy_MM_dd_HH-mm-ss}_{process}_{pid}_{trigger}.log — a snapshot of the ring, which is not cleared, so successive snapshots overlap and logging continues.
  • Off the hot path: severity snapshots are written on the ThreadPool; the file path (directory included) is resolved at trigger time, so a concurrent directory change cannot redirect the write or its prune.
  • Debounce: 5 s — multiple severe events inside the window produce one file (a phase-2 teardown and the FATAL it provokes do not double-write).

Host bridge — AACommDebugLog.Sink

Action<string, string> (source, formatted line): every event line is mirrored to it synchronously, source = the line's identity tag (the connect line's tag carries →endpoint, so hosts routing on source should prefix-match; the one-time header is ring-only). Mirrors GlobalLogger.GlobalDebugLog on the server side; hosts use it to fold AAComm diagnostics into their own session log. Sink and Flush() are the only public surface.

Server log — AACommServerCore.GlobalLogger

Same mechanics (the ring/file core is one source file, owned by AAComm and compiled into AACommServerCore as a linked source — separate assemblies, separate state, so a chatty client can never evict server entries), different policy:

  • Line format: yyyy-MM-dd HH:mm:ss [Debug|Fault|UnhandledException] <source> : <message>.
  • Files in AACommServer_DebugLogs\: {stamp}_Debug.log (the once-on-shutdown save), {stamp}_Flush.log (on-demand snapshot — the client's fire-and-forget CommAPI.FlushDebugLog() verb or the server UI), {stamp}_ImplicitShutdown.log (the abnormal last-client-death save).
  • GlobalDebugLog feeds the server UI's live debug list; LogDebug lines land in both the UI list and the ring.

Joining the two logs

AACommServer identifies clients only by UserId; the client never learns its UserId. The join key is the client→AACS TCP socket, which both sides see from opposite ends:

  • Client side — the connect line logs the socket's local end: 14:02:59.310 [api#1/conn#1→Ethernet 172.1.1.101:5000] channel open (local 127.0.0.1:54321), ServerCompat=Current
  • Server side — on every client Open, one debug line binds UserId to the socket's remote end (the same address:port): 2026-08-24 14:02:59 [Debug] OnAACommRequest() UserId=7 : Open request for 'ET_172.1.1.101' from client endpoint 127.0.0.1:54321

Procedure, starting from either side:

  1. In the client snapshot, find the channel open line for the session of interest → take the local endpoint (127.0.0.1:54321).
  2. Grep the server's debug log for that endpoint → the line names the UserId (7).
  3. Filter the server log by UserId=7 — every server-side event for that client (malformed frames, tx overflow, implicit-shutdown bookkeeping) now correlates with the client's api#N/conn#M timeline. The reverse direction starts from a UserId and greps the endpoint in the client snapshots.

Caveats: ephemeral ports are unique per live connection but recycle over time — on long-uptime machines disambiguate by timestamp proximity; each reconnect is a new conn#M and a new local port, so the join is per-connection, not per-process.

Worked example — attributing a sync-timeout teardown

The failure this layer exists for: an application reports "AAComm disconnected", the server log shows only an unexplained client close. With the snapshots:

14:03:06.694 [api#1/conn#1] sync phase-2 expiry: no reply 402 ms after dispatch at
             14:03:06.291 (budget TimeoutMs 100 + 100 + grace 200 = 400 ms): "APos" → teardown
14:03:06.697 [api#1/conn#1] disconnect (sync-timeout)

tells support: the message reached the wire (phase 2, not a queue abandon), the full grace was spent, the client — not the controller protocol — initiated the close, and the {...}_SyncTimeout.log filename alone already names the trigger. The join procedure then locates the same seconds in the server log under the bound UserId to see what the server observed (e.g. queueing behind another client's long operation).

Known limitations

  • The header's process path is best-effort (Process.MainModule can be inaccessible under permission/bitness constraints; the header then says unknown).
  • The client ring is process-global: snapshots interleave all CommAPI instances (that is what the api#N tag is for).
  • File IO failures are silently swallowed on the client (a diagnostic must never take the host down); the server side falls back to the Windows Event Log as before.
  • The local-port half of the join key is available only from the real socket-backed transports; test doubles log the connect line without it.

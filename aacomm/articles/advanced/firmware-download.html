Firmware & FPGA Download

Overview

Firmware (and, for non-AGM800 products, FPGA) images download over Ethernet or RS-232 — never CAN (see Transport support). AGM800 binary (.bin) firmware is validated via embedded magic markers and an optional .ver file, at parity with the non-AGM800 (.hex FW + .dat FPGA) products.

The surface lives in AAComm/Extensions/: AACommFwInfo validates the file set (ValidateFwFiles) and delegates AGM800 .bin parsing to AACommBinFwInfo, while AACommDownloadFW and AACommDownloadFPGA run the packet loops.

Transport support

FW download runs over Ethernet (AGM800 family — Ethernet only; an AGM800-EC ESI download also over the firmware-sim Simulation channel) or RS-232. It is NOT supported over CAN — AACommDownloadFW (StartDownloading/StartDownloadingSafe) rejects a CAN ConnectionData up front with "Firmware download is not supported over CAN…". The controller's CAN boot-loader FW-data contract is owned by the C2000 flash kernel at 0x100000 (separate from the application image) and is not met by this client path, so a CAN attempt fails controller-side with ERR 43 (unexpected character) / ERR 15 (unexpected byte count). Use Ethernet or RS-232.

The AGD301 FW (.hex) and FPGA (.dat) download paths are HW-validated over RS-232 on both the String and Binary IPC protocols (Agd301HardwareTests, goldens AGD301orAGC301_2D05_V3.0.42.hex + AGD301_for_BissC_and_SinCos_v2.7.2.dat); the FW .hex also flashes over Ethernet (the office rig's AGD301 at 172.1.1.105, by aacomm.cli flash). FPGA download requires normal mode — it rejects BOOT.

The complete gate matrix per download path — product, transport, exact-address and subnet rules, boot mode, file targets, version compatibility — with the CI-rig consequences is docs/ci-cd/fw-fpga-download-constraints.md.

Download paths

AACommDownloadFW picks its path from the connection's product and the target the caller passes:

Connection Target Path File
AGM400, AGM800, Pulse-Sync, AGM800-EC Legacy DownloadFW_MAS02: 700-byte MAS02 packets .bin firmware
AGM800-EC EC_ESI DownloadFW: DownloadESI, then the image as Intel-HEX lines .bin SII image
AGD101-EC, AGD155-EC, AGD156-EC EC_MCU1 / EC_CM / EC_ESI DownloadFW: DownloadFW / DownloadCM / DownloadESI, then Intel-HEX lines .hex; .bin ESI image for EC_ESI
legacy products Legacy DownloadFW: DownloadFW, then the .hex lines .hex

An AGM800-EC SII image and an AGM800-EC firmware image are both .bin files, so the target is the caller's to assert — AAComm never infers ESI from the file, but refuses an EC_ESI file larger than the 16 KiB an ESI image can address, or one that carries firmware identity markers — an SII image does neither. The ESI download runs on the controller's firmware without a boot jump, and connects in full so the controller's own keyword table resolves DownloadESI. An AGM400, AGM800 or Pulse-Sync connection asked for EC_ESI is refused before anything is sent. Every gate per path is in docs/ci-cd/fw-fpga-download-constraints.md.

Remote FPGA identity checks

AACommDownloadFPGARemote downloads a remote .rpd over the AGM800 family's Ethernet connection, including AGM800-EC. AACommRemoteFpgaInfo reads the adjacent seven-line .ver in this order: FPGA Version, FPGA Size, Remote Type, Remote SubType, Remote Variant, Amplifier Version, Comm Version. The metadata is not a payload checksum.

For AGA155 (type 1, subtype 0x0150), compact Remote Variant codes 0x3, 0x6, and 0xA identify 2A03, 2A06, and 2A10 and match CIIdentity[23]. Amplifier Version codes 0x1, 0x2, and 0x3 identify hardware Variant37, Variant47, and Variant46 and match CIIdentity[21]. Comm Version is NA; 8K maps to identity size 2. Marketing strings such as 2A06 are parsed as hexadecimal values, never normalized to the compact codes: select matching compact metadata with compact-identity images.

Normal downloads reject known identity mismatches. For controlled engineering comparisons only, set AACommRemoteFpgaInfo.AllowAga155CurrentRatingMismatch = true to permit current code 6 to 10 or 10 to 6 on a matching AGA155 target. It defaults to false and preserves type, subtype, FPGA size, hardware revision, and communication revision checks. It neither permits current code 3 mismatches nor grants an unknown identity override. AllowForce retains its separate unknown (0/NA) semantics; it does not bypass known mismatches. Both options together preserve the other guards. Firmware that does not expose index 23 retains the legacy download path, without variant validation; enabling the option does not prove that validation occurred.

Remote image transitions

The remote download verifies fresh dual-configuration MSM_CS state: boot (3 or 4) before erase/data writes, and primary (2 or 5) before reporting success. Transition preparation, reconnect acknowledgements and state-read transactions are checked; a successful CIConnect or cached identity alone is insufficient.

Only an exact ERR 151 reply to the final reconfiguration trigger, after successful preparation, is treated as uncertain completion. OnStatus retains the original command/error context, then the service makes one reconnect attempt after its image-start delay and reads the requested image state. Failed or malformed replies, an unconnected target or a wrong image terminate the download. Ordinary offline/flash errors and other trigger errors remain terminal. Erase and data transfer are never automatically repeated. The existing file, identity, force/current-rating, exclusive channel and per-axis access guards apply throughout; the local FPGA path and generic low-level CIConnect contract are unchanged.

Backward Compatibility

  • No .ver file: AGM800 firmware download proceeds without validation, except that an identity-marked image whose product differs from the connection's, when either one is AGM800-EC, is refused
  • .ver file exists: Performs MD5 checksum, version, and product type validation before download

Binary Firmware Parsing (AACommBinFwInfo)

Parses Zynq binary firmware files to extract identity and version information using magic markers embedded in the binary.

Magic Markers

Each marker starts with the signature "AKRB" followed by a type tag:

Marker Tag Payload
Identity IDNT version(4) + size(4) + int32[32] (128 bytes)
Version VERS version(4) + size(4) + char[4][64] (256 bytes)

Byte-order note: Marker types are stored as little-endian 32-bit integers. "IDNT" (0x49444E54) appears as bytes 54 4E 44 49 ("TNDI" in a hex editor). Similarly, "VERS" appears as "SREV".

Extracted Identity Data (32 int32 values)

Index Field
0 Data version
1 Product type
2-6 FW version: Major.Minor.Patch.Owner-Subversion
7 Continuous current limit
8 Peak current limit
9 Number of axes
17 Full scale current
31 Magic end marker (0x12345678)

.ver File Format (AGM800)

Line 1: Version  (optional)  e.g. "3.8.0.0-123"
Line 2: MD5      (optional)  e.g. "MD5:XX-XX-XX-XX-XX-XX-XX-XX-XX-XX-XX-XX-XX-XX-XX-XX"
Line 3: Type     (optional)  e.g. "Type:AGM800"

Valid Type values (prefix match, case-insensitive) depend on the connected product:

Connection Accepted Type: Refused
AGM800-EC (16) AGM800-EC everything else
AGM400 (6), AGM800 (10), PULSE_SYNC (15) AGM800, CiG1-MAS02, MAS02 everything else, AGM800-EC included

AGM800-EC is its own image family: its image and the AGM800 image are not interchangeable, although both are .bin files of the same format.

Validation Steps (when .ver file exists)

  1. MD5 checksum verification (if MD5: line present)
  2. Version match between .ver and binary identity data (if binary contains identity markers)
  3. Product type validation — two independent checks:
    • Binary identity (if the binary contains identity markers): product-type IDs 6=AGM400, 10=AGM800 and 15=PULSE_SYNC share one image and are considered compatible, checked when the .ver has a version line; 16=AGM800-EC matches only itself, checked with or without a .ver
    • Type string (if a Type: line is present): only the values the table above lists for the connected product are accepted. Note: Pulse-Sync is NOT a valid Type string even though product type 15 passes the binary identity check

MAS02 Hex-Encoding (IPC Framing Fix)

MAS02 binary FW packets are raw binary that may contain 0x3E 0x0D — the IPC envelope terminator (>\r). To keep the IPC body ASCII-safe, the client wraps each binary chunk with the @#HEX: sigil (CommCommons.HexEncodedPrefix):

<message-type-prefix>@#HEX:<hex-pairs>\r

The server-side SocketMessageData detects the sigil via IndexOf, strips it, decodes the hex pairs back to raw bytes, and forwards a byte-identical payload to the controller. The per-packet MAS02 header and EOF marker are encoded as hex ASCII strings ("0000" / "FFFF") rather than raw char constants.

This @#HEX: framing is the string-protocol path. Under the default binary (protobuf) IPC the raw FW bytes ride in IpcRequest.PayloadBytes with no hex round-trip — see architecture.md (IPC Framing).

Post-Reset Disconnect Tolerance

Both FW and FPGA download use ResetReplyHelper.IsExpectedPostResetDisconnect after the final packet/batch to handle the race where the controller resets before the OK reply arrives. Disconnect-style replies (ERR 4021, ERR 4020, ERR 4025, channel-fatal) are accepted as success for the last step.

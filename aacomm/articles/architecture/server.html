AACommServerCore

Communication server API for managing hardware communication channels via multiple transport protocols.

Architecture Overview

AACommServerCore acts as a middleware server that manages communication between multiple AAComm client instances and hardware controllers. It binds to a TCP loopback socket (127.0.0.1:399 on Windows, :1024 on Linux) for IPC and handles connection pooling, message queuing, timeouts, and exclusive channel access. It speaks two wire protocols on that one socket — legacy string envelopes and the default binary (protobuf) protocol, detected per client from its first byte; the full wire contract (framing, negotiation, correlation ids, ordering invariants, error codes, compatibility matrix) is AACommComponents/docs/ipc-contract.md.

The loopback IPC is deliberately unauthenticated: the trust boundary is the machine — any local process may open channels or request shutdown. Remote access is a different boundary and must go through its own authenticated listener, never by exposing this socket beyond loopback.

Pipeline Flow Details

Outbound Path (User → Hardware)

  1. TCP Connect: AAComm client establishes TCP connection to AACommServer
  2. Connection Handling: ServerSocketWrapper created with unique UserId
  3. Request Received: Client sends Open/Message/Close request
  4. Request Processing: AACommServerModel.OnAACommRequest() deserializes and routes message
  5. Channel Routing: Message routed to appropriate ChannelHandler by ChannelKey
  6. Message Queuing: ChannelHandler.Send() enqueues the message
  7. Hardware Send: ChannelHandler.PumpLocked() dequeues the next message (one in-flight per channel), starts the timeout timer, and sends via ICommunicator
  8. Protocol Transmission: ICommunicator implementation sends using protocol-specific format

Inbound Path (Hardware → User)

  1. Hardware Response: Physical hardware responds via protocol (CAN/RS-232/Ethernet)
  2. Receive Callback: ICommunicator.OnMsgReceived callback invoked with response data
  3. Reply Processing: ChannelHandler.OnMsgFromHW() stops the timer and enqueues the reply on the channel's ordered delivery lane (drained outside the lock)
  4. Message Forwarding: AACommServerModel.OnMessageFromHardware() formats per the client's protocol and forwards to its socket
  5. TCP Response: ServerSocketWrapper.Send() enqueues on the client's single-writer outbound queue
  6. Queue Processing: ChannelHandler.PumpLocked() dispatches the next queued message

Key Features

Multi-User Channel Sharing

  • Multiple AAComm clients can share the same hardware channel
  • ChannelHandler tracks NumOfUsers per channel
  • Channel closes only when last user disconnects

Exclusive Access Mode

  • Clients can request exclusive channel access via StartExclusiveAccess()
  • Other users' messages rejected with CHANNEL_IS_EXCLUSIVE error
  • Prevents concurrent access during critical operations

Timeout Management

  • Each message carries its own timeout (TimeoutMs, default 2000 ms); the full timeout/limit table is in AACommComponents/docs/ipc-contract.md
  • Timer started on send, stopped on receive
  • Timeout triggers fatal error and channel closure

Message Queuing & Channel Lifecycle

  • FIFO queue per channel ensures sequential message processing; server-internal (IA:) queries ride the same queue, so per-client replies always arrive in request order
  • Only one hardware message "in-flight" per channel at a time
  • Channel state machine (Open / Resetting / Dead): slow operations — the communicator open, the post-Reset recovery wait, Ethernet reconnect retries — run as states on worker tasks, never as threads parked under a lock, so one channel's slow phase cannot stall message routing on other channels or clients
  • Replies to clients are collected under the channel lock into a per-channel ordered delivery lane and written outside it; each client socket additionally has a dedicated single-writer outbound queue (ServerSocketWrapper), so a client that stops reading blocks only its own writer and is evicted on send timeout or queue overflow
stateDiagram-v2
    [*] --> Open : constructed Open (registry ctor is cheap; the communicator opens later, off the registry lock — dispatch can't run before Open commits a user)
    Open --> Resetting : reset request OK'd (PostResetWaitMs > 0, or legacy 10001/10002 marker)
    Resetting --> Open : recovery worker done (wait elapsed; Ethernet reopened, bounded retries)
    Resetting --> Dead : closed/evicted during recovery, or reopen retries exhausted (fatal)
    Open --> Dead : FATAL (timeout / link lost / send failure), or Dispose (last-user close marks eviction; the registry's eviction disposes)
    Dead --> [*] : registry eviction, posted off-lock (EvictionPending keeps revived channels safe)

Slow work (the communicator open, the recovery wait, reopen retries) always runs on worker tasks in a state, never on a thread parked under a lock — Resetting and Dead are what make that safe: dispatch refuses in both, and the recovery worker alone owns the Resetting → Open transition. (The state field is born Open at construction; nothing can dispatch until the first Open commits a communicator and a user, so the window is inert.)

Buffer Management

  • Client socket receive buffer: 100,000 bytes
  • Ethernet hardware buffer: 256 KB (262,144 bytes)
  • Wire framing (string envelope vs binary length-prefix) per protocol: see AACommComponents/docs/ipc-contract.md

Error Handling

  • Fatal errors (timeout, connection loss) close the channel and notify every user of it: in-flight/queued users get the fatal as their reply; passive users are notified too — as a CHANNEL_EVENT frame for binary clients that declared the capability on Open, or the legacy fatal shape otherwise. Client sockets close after the fatal flushes — best-effort with bounded backpressure (tx-queue overflow / send-timeout still hard-closes; see AACommComponents/docs/ipc-contract.md §Fatal broadcast).
  • Unsent messages cleared on user disconnect
  • Automatic reconnection logic for Ethernet after Reset

Supported Hardware Protocols

  • CAN Bus: Kvaser CANlib-based communication (Windows or Linux)
  • RS-232: Serial port communication
  • Ethernet: TCP/IP socket-based communication with bulk message support (up to 50 messages per bulk)
  • Simulation: managed firmware-sim — the server spawns firmware_sim locally over loopback and bridges it (Communicator_FirmwareSim). The legacy file-based Simulator channel is removed; the Simulator enum survives only as the in-process echo channel for the AAComm virtual-test harness.

Spawned-child lifetime

A spawned firmware_sim is started bound to the server process by ChildProcessReaper.StartReaped, so it is reaped when the server dies for any reason — including a hard crash or external kill, where the graceful Shutdown()/Dispose() teardown never runs. The mechanism is per-OS:

  • Windows — a kill-on-close Job Object (JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE): the child is assigned to a process-wide job; when the server's last job handle closes, the OS terminates the job. Kernel-enforced.
  • Linux — prctl(PR_SET_PDEATHSIG, SIGKILL), applied by launching the child through setpriv --pdeathsig (util-linux) since .NET has no pre-exec hook. The death-signal is keyed to the forking task, so the fork runs on a process-lifetime spawner thread (else a transient caller thread exiting would SIGKILL a healthy sim). Logged no-op fallback if setpriv is absent.
  • macOS — deferred with the osx native build (issue #101); the crash-safe equivalent is a kqueue NOTE_EXIT babysitter. Graceful Dispose/Close still reaps the child; only an abnormal server exit can orphan it.

The IPC listen socket is also made non-inheritable (HandleInheritance) so a spawned child (started with bInheritHandles=TRUE for stdio redirect) never inherits it and pins the IPC port after the server exits — Windows-only, since .NET Core already creates non-inheritable sockets on Linux/macOS.

Events

  • OnLog: Tx/Rx message logging
  • OnLogDebug: Debug events and errors
  • OnClientAdded: New client connected to channel
  • OnClientRemoved: Client disconnected from channel
  • OnMsgReceived: Message received from hardware (for counting)
  • OnKillRequest: Server shutdown requested by last client

Relationship to AAComm

AACommServerCore is the server middleware, AAComm is the client library.

  • AACommServerCore: Standalone process, manages hardware connections, handles multiple clients
  • AAComm: Embedded in user applications, provides high-level API

Multiple AAComm clients can connect to a single AACommServerCore instance, sharing hardware channels. See AAComm/docs/architecture.md for the client-side architecture and AACommComponents/docs/ipc-contract.md for the wire contract between the two.

Packet Sniffer

AACommServerCore defines the host-facing sniffer contract — IChannelSnifferHook + the SnifferConnectionInfo DTO (in Sniffing/) — and exposes SnifferHook on AACommServerModel as the integration point. When an Ethernet or managed Simulation channel opens, the server maps ConnectionData to SnifferConnectionInfo and calls IChannelSnifferHook.OnChannelOpened; on close it calls OnChannelClosed(SnifferConnectionInfo, bool). The endpoint captured at open is reused at close (a sim's Close request carries no endpoint of its own), so the notifications always match. A managed sim's loopback port is single-use, so its SnifferConnectionInfo.IsEphemeral is set — the sniffer discards that context on close (raising OnNicRemoved) instead of keeping it Paused for a reconnect that can never come. Notifications carry the controller endpoint, so a host can capture several controllers concurrently and route each close to the right capture.

The concrete sniffer (SnifferService) and all SharpPcap/Npcap-bound implementation live in the AACommSniffer project, which references AACommServerCore and implements the contract. The dependency runs AACommSniffer → AACommServerCore, not the reverse — so AACommServerCore carries no SharpPcap dependency and builds platform-agnostic (a Linux AACommServerNative has no capture library in its graph unless it explicitly wires the sniffer). See ../AACommSniffer/sniffer.md for the full API and documentation.

Sniffer feature details

The capture feature (NIC selection, ring buffer, session snapshots, filter modes, config knobs, host UI, threading, failure modes) is documented in full — and without duplication — in ../AACommSniffer/sniffer.md. The sniffer multi-targets net48 + net8.0 and detects its capture backend per platform (Npcap on Windows, libpcap on Linux/macOS) via PcapDetector.

Build Notes

.NET SDK 10 Compatibility

When building with .NET SDK 10 targeting .NET Framework 4.8, non-string resources (like icons) require special handling. The AACommServer project loads its tray icon via Assembly.GetManifestResourceStream() instead of the designer-generated Resources class to avoid System.Resources.Extensions version conflicts.

Class LockEventWriteOrder

Namespace
AAComm.Services

The write order a parameter restore needs under the lock/event guards of firmware that declares LockEventMode up to 2 (see Mode2Supported(MessageData)). In LockEventMode 1 and 2 that firmware refuses a change to a lock/event dependency while LockEn or EventOn is on (error 403), and refuses LockEn/EventOn after a dependency changed until the offset is recomputed (404; 335 if it was never computed).

Per axis, when the rows touch a dependency or LockEventMode, the order becomes: LockEn and EventOn off (both, whether or not the rows carry them: a .par has neither, and either one armed refuses the change), then the other rows in their original order, then LockEventMode, then LockEventInit when the axis is in mode 1 at re-arm, then the rows' own LockEn/EventOn in their order, so the last one requested is the state left. Axes whose rows touch neither keep their rows untouched and in place.

The mode at re-arm is the rows' LockEventMode when they carry one, otherwise the controller's current mode (ReadCurrentModes(IList<string>, Func<AACommMessage, AACommEventArgs>)). An AGM800-EC enable forces mode 2 only at the next enable, so an AGM800-EC restored into mode 1 gets the LockEventInit like any other controller.

Dependencies

The keywords whose change invalidates the lock/event offset; EncFilt, AuxEncFilt and CurrDir are not among them. The firmware counts AuxEncDir only with the aux source (EncSinCosHWEn=3) and VEncFact/VEncFactDen only with the virtual-encoder source (2); the order treats them as dependencies always, since a row can't tell which source the controller will have when it lands, and disarming first is harmless.

ReadCurrentModes(IList<string>, Func<AACommMessage, AACommEventArgs>)

Reads the current LockEventMode (<axis>LockEventMode) of each axis whose rows touch a lock/event dependency but carry no LockEventMode row, for Order(IList<string>, Func<string, bool>, Func<char, int?>)'s currentMode. An axis whose read failed (an error reply, a reply that isn't a number, or a throw) maps to null: without its mode the LockEventInit decision can't be made, so the caller writes nothing. sendReceive is a synchronous send; never call this from a reply callback.

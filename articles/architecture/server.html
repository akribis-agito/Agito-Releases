AACommServerAPI

Communication server API for managing hardware communication channels via multiple transport protocols.

Architecture Overview

AACommServerAPI acts as a middleware server that manages communication between multiple AAComm client instances and hardware controllers. It binds to a TCP loopback socket (127.0.0.1:399 on Windows, :1024 on Linux) for IPC and handles connection pooling, message queuing (with >\r message delimiters), timeouts, and exclusive channel access.

Pipeline Flow Details

Outbound Path (User → Hardware)

  1. TCP Connect: AAComm client establishes TCP connection to AACommServer
  2. Connection Handling: ServerSocketWrapper created with unique UserId
  3. Request Received: Client sends Open/Message/Close request
  4. Request Processing: AACommServerModel.OnAACommRequest() deserializes and routes message
  5. Channel Routing: Message routed to appropriate ChannelHandler by ChannelKey
  6. Message Queuing: ChannelHandler.Send() enqueues message and starts timeout timer
  7. Hardware Send: ChannelHandler.SendNextMessage() dequeues and sends via ICommunicator
  8. Protocol Transmission: ICommunicator implementation sends using protocol-specific format

Inbound Path (Hardware → User)

  1. Hardware Response: Physical hardware responds via protocol (CAN/RS-232/Ethernet)
  2. Receive Callback: ICommunicator.OnMsgReceived callback invoked with response data
  3. Reply Processing: ChannelHandler.OnMsgFromHW() stops timer, sends reply to client
  4. Message Forwarding: AACommServerModel.OnMessageFromHardware() forwards to socket
  5. TCP Response: ServerSocketWrapper.Send() transmits response back to client
  6. Queue Processing: ChannelHandler.SendNextMessage() processes next queued message

Key Features

Multi-User Channel Sharing

  • Multiple AAComm clients can share the same hardware channel
  • ChannelHandler tracks NumOfUsers per channel
  • Channel closes only when last user disconnects

Exclusive Access Mode

  • Clients can request exclusive channel access via StartExclusiveAccess()
  • Other users' messages rejected with CHANNEL_IS_EXCLUSIVE error
  • Prevents concurrent access during critical operations

Timeout Management

  • Each message has configurable timeout (TimeoutMs, default 2000ms)
  • Common timeouts: Reset (10001ms standard controller, varies by type), Firmware (6000ms), User Program (3000ms)
  • Timer started on send, stopped on receive
  • Timeout triggers fatal error and channel closure
  • After-reset wait periods: Standard controller (1500ms), MAS02 (4000ms)

Message Queuing

  • FIFO queue per channel ensures sequential message processing
  • Only one message "in-flight" per channel at a time
  • Prevents race conditions and ensures deterministic responses
  • Lock-based synchronization (_QueueSyncObj) for thread safety

Buffer Management

  • Client socket receive buffer: 100,000 bytes
  • Ethernet hardware buffer: 256 KB (262,144 bytes)
  • Message format: <ConnectionData>#@#<MessageType>#@#<TimeoutMs>#@#<Message>>\r
  • Internal message separator: #@#

Error Handling

  • Fatal errors (timeout, connection loss) close channel and notify all users
  • Unsent messages cleared on user disconnect
  • Automatic reconnection logic for Ethernet after Reset

Supported Hardware Protocols

  • CAN Bus: Kvaser CanLib-based communication (Windows only)
  • RS-232: Serial port communication
  • Ethernet: TCP/IP socket-based communication with bulk message support (up to 50 messages per bulk)
  • Simulator: File-based simulation for testing (when AllowSim enabled)

Events

  • OnLog: Tx/Rx message logging
  • OnLogDebug: Debug events and errors
  • OnClientAdded: New client connected to channel
  • OnClientRemoved: Client disconnected from channel
  • OnMsgReceived: Message received from hardware (for counting)
  • OnKillRequest: Server shutdown requested by last client

Relationship to AAComm

AACommServerAPI is the server middleware, AAComm is the client library.

  • AACommServerAPI: Standalone process, manages hardware connections, handles multiple clients
  • AAComm: Embedded in user applications, provides high-level API

Multiple AAComm clients can connect to a single AACommServerAPI instance, sharing hardware channels. See ../AAComm/ARCHITECTURE.md for the client-side architecture.

Packet Sniffer

The sniffer hook (IChannelSnifferHook) and all sniffer implementation have moved to the AACommSniffer project. See ../AACommSniffer/ for the full API and documentation.

AACommServerAPI references AACommSniffer and exposes SnifferHook on AACommServerModel as the integration point. When an Ethernet channel opens, the server maps ConnectionData to SnifferConnectionInfo and calls IChannelSnifferHook.OnChannelOpened; on close it calls OnChannelClosed.

Packet Sniffer Details (Windows/.NET Framework 4.8 only)

AACommServerAPI includes an optional packet capture feature for debugging Ethernet communication issues. The sniffer captures raw network traffic on the interface used for controller communication.

Requirements

  • Npcap: Must be installed (https://npcap.com) - the sniffer gracefully degrades if Npcap is not available
  • Windows: Sniffer functionality is only available on .NET Framework 4.8 (not .NET 6/8)
  • SharpPcap: NuGet package (automatically included for net48 target)

Features

  • Automatic capture: Starts capturing when an Ethernet channel opens (if enabled)
  • Smart NIC selection: Automatically selects the correct network interface based on target IP subnet
  • Filter modes:
    • Wide: Capture all traffic on the NIC
    • Focused: Capture only AAComm traffic (filtered by controller IP and port using BPF)
  • Session snapshots: Creates timestamped capture snapshots on disconnect:
    • Error/: Unexpected disconnects (socket errors, cable unplug, timeout, fatal errors)
    • User/: Normal user-initiated disconnects (click Disconnect in PCSuite)
    • Marked/: Manual "Mark Capture" button clicks
  • Ring buffer: Rolling capture files with configurable size limits (default 50MB per file, 10 files)
  • Retention policies: Configurable number of snapshots to retain per event type (default: 10 Error, 3 User, 5 Marked)
  • Clean session start: _current folder is cleared when a new Ethernet connection starts
  • TCP handshake capture: 500ms delay on disconnect ensures full TCP close handshake (FIN/ACK) is captured

UI Integration (AACommServer Window)

The AACommServer window includes a sniffer status panel:

  • Status indicator: Shows Capturing (green), Paused (yellow), or Unavailable (gray)
  • Statistics: Packet count and bytes captured
  • Enable checkbox: Toggle sniffer on/off
  • Mark Capture button: Manually trigger a snapshot
  • Open Folder button: Open sniffer directory in Explorer

If Npcap is not installed, a message "Packet sniffer unavailable (Npcap not installed)" is shown.

API

// Access the singleton
var sniffer = SnifferService.Instance;

// Check availability
if (sniffer.IsNpcapInstalled)
{
    // Start/stop/pause capture
    sniffer.Start(connectionData);
    sniffer.Pause();
    sniffer.Resume();
    sniffer.Stop();

    // Trigger manual snapshot
    sniffer.TriggerSnapshot(SnifferEventType.Marked);

    // Export capture to specific folder
    string exportPath = sniffer.ExportCapture(@"C:\Temp\Captures");

    // Get statistics
    string stats = sniffer.GetStatisticsString(); // "1,234 pkts, 2.5 MB"
}

Events

  • OnStatusChanged: Sniffer status changed (Capturing/Paused/Unavailable)
  • OnStatisticsUpdated: Packet count and bytes captured updated (every 100 packets)
  • OnSnapshotCreated: Session snapshot created (provides event type and path)

Build Notes

.NET SDK 10 Compatibility

When building with .NET SDK 10 targeting .NET Framework 4.8, non-string resources (like icons) require special handling. The AACommServer project loads its tray icon via Assembly.GetManifestResourceStream() instead of the designer-generated Resources class to avoid System.Resources.Extensions version conflicts.

See AACommServer/DOTNETSDK10_RESOURCE_FIX.md for detailed analysis.

    读懂 AAComm 日志¶

    Windows 下先打开 %LOCALAPPDATA%\PCSuite\。记下故障时间和时区、控制器地址或仿真型号、应用版本和失败的 API，再按问题选日志。

    要查什么 日志
    客户程序为什么连不上、超时或主动拆链 AAComm_DebugLogs 下的 AAComm 客户端诊断日志。_SyncTimeout.log、_Fatal.log 和 _Flush.log 是环形缓冲区的快照，文件内容可以重叠。
    服务器怎样打开通道、收到哪些连接事件 AACommServer_DebugLogs 下的服务器诊断日志。_Debug.log 在正常退出时保存，_Flush.log 是手动快照，_ImplicitShutdown.log 表示最后一个客户端异常退出后服务器收尾并退出。
    逐条核对请求与回复 支持界面的 AACommServer 中单独保存通信日志；已有 Sniffer 捕获可在 AACommServer_DebugLogs\Sniffer 查找。诊断日志不会记录完整的命令流。
    PCSuite 上发生了哪个操作、何时出现错误 PCSuite_DebugLogs 下的 PCSuite 会话日志。

    把客户端和服务器的记录对上¶

    14:02:59.310 [api#1/conn#1→Ethernet 192.0.2.10:5000] channel open (local 127.0.0.1:54321), ServerCompat=Current
2026-11-20 14:02:59 [Debug] OnAACommRequest() UserId=7 : Open request for 'ET_192.0.2.10' from client endpoint 127.0.0.1:54321
    1. 客户端时间精确到毫秒。先找对应控制器的 channel open，记下 api#1/conn#1 和 local 后的地址及端口。api#1 表示一个 API 实例，conn#1 表示该实例的第一次成功打开。
    2. 在同一时段的服务器日志里搜索 127.0.0.1:54321。例如这次能找到 UserId=7。local 后的地址是客户端连到服务器的本地端点，和控制器地址是两个不同的地址。
    3. 客户端按 api#1/conn#1 过滤，服务器按 UserId=7 分析。重连后重新配对。临时端口可能复用，匹配时同时核对时间。

    判断是哪一段超时¶

    客户端记录 可以判断什么
    sync phase-1 expiry: abandoned in queue 该请求还在客户端队列中就被放弃，未分派。这次超时不会拆链。
    sync phase-2 expiry: no reply … after dispatch，随后 disconnect (sync-timeout) 请求已离开客户端队列，等待回复超时后客户端拆链。是否到达控制器、是否执行，需要用通信记录和回读确认。
    server FATAL received 或 comms error/FATAL 查看同一连接标记下最早的异常，再对照服务器事件和关闭原因。

    例如 APos 出现 phase 2，而服务器只记录了客户端关闭，先按上面的端点定位服务器记录，再查同一时段是否有通信捕获。交换日志时保留时间、连接标记和错误码，按需遮盖设备地址、路径和工艺参数。

    另见连接故障诊断和通信层错误码。

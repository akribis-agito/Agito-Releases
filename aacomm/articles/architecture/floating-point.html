AAComm Floating-Point Resolution

Principle

Data that leaves AAComm via the Extension classes (e.g., RecordingDataContainer, LoggerDataContainer, ScopeDataContainer, AllStatInterpreter) is properly resolved and ready to use. Raw IEEE 754 bit-pattern resolution is handled transparently by these classes.

Limitation: Resolution only applies when data is obtained through the Extension mechanism, or for protocols that have Rx-path resolution (see below). If an unsupported upload command is issued directly via CommAPI.Send() — such as from PCSuite Terminal — the raw response is not resolved. The consumer receives unprocessed bit-masked values.

ConFltSnapVal and ProgSnapVal cannot be auto-resolved via an Extension mechanism because the snapshot source parameters (ConFltSnapSrc / ProgSnapSrc) are user-configurable — the parameter types are unknown until the CCC sources are queried at runtime.

Resolution

Core logic lives in FloatHelper (AAComm.Services) — public static class, callable directly by all consumers.

FloatHelper.ResolveFloatingPoint(MessageData md, long val, bool doubleSupported, bool floatSupport) determines the correct conversion based on the parameter's MessageData type:

  • float/double with doubleSupported — LongToDouble() (64-bit IEEE 754)
  • float with !doubleSupported and floatSupport — IntToFloat() (32-bit IEEE 754)
  • float with !doubleSupported and !floatSupport — returned as-is (float hole protection)
  • int / long — returned as-is
  • null metadata (unknown parameter) — returned as-is (safe fallback)

FloatHelper.ResolveFromCCC(int ccc, long rawVal, IMessagesContainer dataContainer, bool doubleSupported, bool floatSupport) resolves via Complex CAN Code: parses CCC -> looks up MessageData -> delegates to ResolveFloatingPoint.

Throws FormatException on NaN or Infinity.

Float Hole Protection

AllStat_64bit protocols (AllStat, Logger, Scope, ConFltSnap, ProgSnap) never transmit 32-bit float bit patterns. They either send raw integers or 64-bit doubles. These protocols pass floatSupport: false, which blocks the IntToFloat path and prevents garbage values when doubleSupported=false and a parameter has float metadata. RecUpload and ParamAbout pass floatSupport: true.

Firmware-Side UserUnits (Recording Header)

The per-vector UserUnits integer stored in the recording header (VectorDataContainer.UserUnits, read from GetUserUnitsIndex(i)) is part of a parallel firmware-level scaling system. It is mutually exclusive with the PCSuite UU feature at the firmware level. This value is preserved as metadata in RecParamHeader and AGF files but is NOT used for PCSuite UU scaling. PCSuite UU factors are looked up dynamically via CommAPI.GetUserUnitsEnabled() + ControllerMessagesContainer.TryGetUserUnitAxis() through the centralized FloatHelper.ApplyUserUnits() method.

Double Support Flags

LoggerUpload / ScopeUpload

Both use PacketDataParser for the common wire format: nPackets, [header, val1, val2, ...], ..., 0. Header is packet ID (Logger) or Time (Scope). Resolution is applied per value using the caller-provided MessageData list.

PCSuite adapts these containers into its UI models. The CSV import path in LoggerData bypasses AAComm resolution (values are already resolved in the file).

AllStat

AllStatInterpreter requires a connected CommAPI (constructor delegates validation to RecParamsResolver.ValidateAPI). Every field in AllStatAxisData is resolved via mnemonic lookup against the controller's MessagesContainer — float/double fields get bit-pattern conversion, integer fields pass through as double.

Rx-Path Resolution (ConvertReplyToFloatIfNeed)

FloatHelper.ConvertReplyToFloatIfNeed is the inline Rx-path resolver for all message replies. It intercepts raw controller replies before delivery to the caller and converts IEEE 754 bit patterns to floating-point values. This ensures that even low-level SendReceive() consumers (e.g., PCSuite Terminal) receive properly resolved data.

Resolved in the Rx path:

  • Single-value parameters: float (IntToFloat) and double (LongToDouble) based on MessageData type. Note: the single-value path dispatches purely on MessageData.IsFloat/IsDouble — it does NOT check the doubleSupported/floatSupport flags.
  • ParamAbout: multi-value State,MIN,MAX,DEFAULT — delegated to FloatHelper.ResolveParamAbout
  • AllStat: multi-value comma-separated longs per axis/group — delegated to AllStatInterpreter.ResolveRawReply. Uses the static mnemonic arrays and the private Resolve() instance method to convert each value in group order. Returns reply unchanged if !AllStat_64bit_Supported.

NOT resolved in the Rx path (CAN code unknown at Rx flow time):

  • RecUpload: not resolved here — RecordingDataContainer parses raw longs and resolves per-vector with the correct feature flags. Rx-path resolution would double-convert (long→string→long parse failure)
  • RecUploadNext: sequential packet protocol — the CAN codes are not embedded in the N2 data packets
  • ScopeUpload / LoggerUpload: the CAN codes are supplied by the caller, not present in the reply
  • ConFltSnapVal / ProgSnapVal: snapshot source CCCs are user-configurable and unknown without runtime query

Error Handling

AAComm throws generic FormatException on invalid floating-point values (NaN, Infinity). Consumer applications (e.g., PCSuite) catch and localize these messages.
